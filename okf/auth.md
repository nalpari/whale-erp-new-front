## 로그인 · 세션

* 로그인은 **아이디**와 비밀번호로 한다. 이메일로 하지 않는다. 아이디 저장을 두고, 아이디 찾기가 따로 있는 것도 이 때문이다 — `S-XJDKSI` · `AUTH-1`
* 로그인에 성공하면 계정 유형에 따라 접속 사이트를 나눈다. BP·가맹 마스터·관리자는 웨일ERP(BP) 홈, 플랫폼 마스터·관리자는 웨일ERP(플랫폼관리) 사이트로 간다 — `F-DZVFIC`
* 플랫폼관리 사이트에는 홈이 없다. 플랫폼 계정은 로그인하면 계정에 등록된 플랫폼 메뉴 가운데 조회 권한과 주소가 있는 첫 메뉴(헤더에 보이는 순서상 첫 화면)로 간다. 비밀번호 강제 변경 · 약관 동의를 마치기 전에는 넘어가지 않는다 (2026-10-28 재영)
* 아이디는 영문 또는 영문·숫자 4~20자다. 탈퇴·삭제한 계정의 아이디도 다시 쓸 수 없다. 로그인 화면에서는 형식을 검사하지 않고 빈칸만 막는다(2026-10-28 재영). 빈칸은 브라우저 말풍선 대신 칸 아래에 「아이디를 입력해주세요.」 · 「비밀번호를 입력해주세요.」로 알리고, 둘 다 비면 둘 다 보인 뒤 첫 빈칸으로 커서를 옮긴다 — `S-XJDKSI` · `PL-OCJOFP`
* 연속 5회 틀리면 5분 잠근다. 잠긴 동안은 아이디·비밀번호를 확인하지 않는다. 풀리는 길은 5분 경과 · 임시 비밀번호 발급 · 운영자의 비밀번호 초기화(BP 마스터 · BP 관리자 · 플랫폼 관리자 관리) 셋이고, 잠금만 푸는 버튼은 1차에 없다(2026-10-28 재영 — BP 마스터 · 플랫폼 관리자 초기화의 잠금 해제는 api #179). 잠긴 동안의 문구는 「로그인이 잠겼습니다. 5분 뒤에 다시 시도하거나 임시 비밀번호를 발급받아 주세요」이다. 비밀번호 찾기 링크는 이 안내에 따로 두지 않고, 화면에 늘 있는 「아이디/비밀번호 찾기」 링크로 안내한다(2026-10-28 재영) — `F-DZVFIC`
* 실패 횟수는 성공한 로그인 사이에 틀린 횟수다. 시간이 지나도 줄지 않아, 며칠에 걸쳐 틀려도 성공 없이 5회째면 잠긴다. 세는 것은 있는 계정(미사용 포함, 탈퇴·삭제 제외)의 비밀번호·임시 비밀번호 불일치뿐이고, 잠긴 동안의 시도는 세지 않으며 해제 시각도 늘리지 않는다. 5회째 실패에는 바로 잠김 문구로 답한다. 횟수는 로그인 성공 · 임시 비밀번호 발급 · 운영자의 비밀번호 초기화 때 0 이 되고, 5분 잠금이 끝난 뒤의 첫 실패는 1회째로 다시 센다 (api `attempt-lock.ts` · `admin-auth.service.ts` 구현 기준, 2026-10-28) — `F-DZVFIC`

* 서버가 꺼졌거나 5xx · 깨진 응답이면 「시스템 오류로 로그인할 수 없습니다. 잠시 후 다시 시도해 주세요.」, 요청이 너무 많아 api 가 막으면(429, 잠금 아님) 「요청이 많습니다. 잠시 뒤 다시 시도해 주세요」다 — `S-XJDKSI`

## 계정 찾기

* 본인 확인은 등록한 **이름·이메일** 대조다. 비밀번호 찾기는 아이디까지 맞춘다. 휴대전화 본인인증은 쓰지 않는다 — `S-PHOPWY` · `S-EOMSRG` · `AUTH-2`
* 비밀번호를 되찾는 수단은 등록 이메일로 보내는 **임시 비밀번호**다. 들어오면 강제로 바꾸게 한다 — `S-EOMSRG` · `PL-QSBSYY` · `AUTH-2` · `AUTH-4`
* 메일 발송은 3팀이 맡으므로 발송 포맷은 3팀이 만든다 — `AUTH-4`
* 아이디 찾기는 사용 상태 계정만 대상이다. 찾으면 앞 2자와 뒤 1자만 보인다. 가리는 일은 api 가 하고 전체 아이디는 front 로 오지 않는다 — `S-PHOPWY`
* 아이디 찾기에도 요청 제한을 둔다 — IP 1분 30회(이메일 찾기와 같은 전용 한도)와 이메일 하나에 10분 10회(api 기본 계정 축). 이메일 하나에 이름을 바꿔 가며 아이디를 알아내는 시도를 막는 것이 계정 축뿐이라서다. 처음 정책의 「횟수 제한 없음」을 고쳤다(2026-10-19 재영). api 는 1팀에 요청했다(`POST /auth/admin/login-id-find-attempts`)
* 일치하는 계정이 없거나 미사용·탈퇴 계정과만 일치해도 같은 문구다. 계정이 있는지 드러내지 않는다 — `S-PHOPWY`
* 임시 비밀번호는 12자, 1시간 유효, 계정당 1시간 5회다. 횟수는 이메일이 아니라 계정 기준으로 센다 — `S-EOMSRG`
* 다시 받으면 앞의 임시 비밀번호는 바로 만료된다. 메일이 나가지 않으면 임시 비밀번호도 활성화하지 않는다 — `S-EOMSRG`
* 비밀번호 찾기도 아이디 찾기처럼 일치 여부를 확인해 알린다(2026-10-20 재영 — 2026-10-19 의 「결과 안내 하나」를 바꿨다). 일치하는 사용 중 계정이 없으면(미사용 · 탈퇴 계정과만 맞아도) 「회원정보를 찾을 수 없습니다. 입력하신 정보와 일치하는 회원정보가 없습니다. 이름, 아이디, 이메일 주소를 다시 확인해 주세요.」, 발급되면 「이메일을 확인해 주세요. 입력하신 이메일 주소로 임시 비밀번호를 발송했습니다. 임시 비밀번호는 발급 후 1시간 동안 사용할 수 있습니다.」. 지금 api 는 일치 여부 · 메일 발송 여부와 상관없이 같은 202 라 일치 없음을 404 로 주도록 바꿔 달라고 요청했다 — 그 전엔 늘 발송 안내가 뜬다. 응답이 10초를 넘기면 발송 안내로 끝내고, 1시간 5회 초과(429)는 따로 알린다. 아이디 찾기의 일치 없음은 「입력하신 정보와 일치하는 회원정보가 없습니다. 이름, 이메일 주소를 다시 확인해 주세요.」다. 화면 안내 문구는 탭마다 「회원가입 시 등록한 이름, (아이디,) 이메일 주소를 입력해 주세요.」. api 가 메일 발송 중 오류(503 + code TEMPORARY_PASSWORD_SEND_FAILED, api #77)면 「임시 비밀번호 메일 발송을 확인하지 못했습니다. 몇 분 안에 메일이 오지 않으면 다시 요청해 주세요.」 — Gmail 과 통신하다 끊겨 메일이 갔을 수도 있어 단정하지 않는다(2026-10-20 api 요청). 그 밖의 5xx 면 「처리 결과를 확인하지 못했다 — 메일이 오지 않았거나 받은 임시 비밀번호로 로그인되지 않으면 다시 요청」으로 안내한다. api 는 메일을 보낸 뒤 발급을 한 트랜잭션으로 저장해, 5xx 는 메일 전 실패 · 메일 뒤 저장 실패(온 메일은 못 쓰고 앞의 것이 살아 있다) · 발급을 마친 뒤의 게이트웨이 오류가 섞여서다(PR #56 리뷰)
* 화면은 한 화면 두 탭(「ID 찾기」 · 「비밀번호 찾기」)이고 주소 `#id` · `#pw` 로 탭을 고른다. 로그인한 채 들어오면 권한별 홈으로 보낸다. 칸이 비었거나 이메일 형식이 틀리면 제출 버튼(「아이디 확인」 · 「임시 비밀번호 받기」)이 막힌다. 브라우저는 통과시키지만 api 가 거절하는 형식(예: `a@b`)이면 「이메일 형식이 올바르지 않습니다.」(2026-10-23 — 이메일 칸 공통 문구, api 에 묻기 전에 front 가 같은 규칙으로 먼저 본다), 요청 제한에 걸리면 「요청이 많습니다. 잠시 뒤 다시 시도해 주세요」다. 아이디 찾기는 응답이 10초를 넘기거나 서버 오류면 「서버에 연결하지 못했습니다. 잠시 뒤 다시 시도해 주세요」다. 버튼 줄은 두 탭 모두 「주 동작 · 회원가입 · 로그인 이동」이다(2026-10-20, 구현 기준).
* 발급해도 기존 비밀번호는 살아 있다. 기존 비밀번호로 먼저 들어오면 쓰지 않은 임시 비밀번호는 무효가 되고, 임시 비밀번호로 들어와 새 비밀번호를 정하면 둘 다 만료된다 — `S-EOMSRG`
* 잠긴 계정도 발급받을 수 있고, 발급하면 잠금이 풀린다 — `S-EOMSRG`
* 로그인에 성공하면 권한 유형으로 영역이 갈린다 — 플랫폼 마스터·관리자(PM·PA)는 `/platform`, BP·가맹 계정(BM·BA·FM·FA)은 `/home`. `/platform` 은 화면이 아니라 첫 플랫폼 메뉴로 넘겨 주는 주소다 — `SessionGate` 가 login-info 의 메뉴로 `firstMenuUrl` 을 골라 `replace` 하고, 첫 메뉴가 없을 때만 권한 요청 안내를 그린다. 헤더 로고 · 플랫폼관리 바로가기도 플랫폼 탭에서는 첫 메뉴를 바로 가리킨다. 임시로 여는 알림 템플릿 관리는 api 메뉴 행이 생기기 전까지 첫 메뉴 후보가 아니다 (2026-10-28). 로그인 전 화면은 상단 메뉴와 푸터가 있는 사이트형 레이아웃이고, 로그인 뒤는 같은 헤더에 메뉴만 다른 ERP·플랫폼 레이아웃이다. 구현은 [Whale ERP Frontend](/whale-erp-front.md) 를 본다 (2026-10-12).
* 비밀번호 오류 문구는 화면이 따로 만들지 않고 비밀번호 정책의 문구를 그대로 쓴다 — `PL-QSBSYY`

## 약관

* 가입에서 받는 1)·2) 와 직원 근무 앱에서 받는 약관을 대상별로 묶어 둔다. 푸터의 약관 링크는 약관 전문 페이지 `/terms` 로 간다(2026-10-19 재영). 강제 비밀번호 변경의 재동의는 팝업이다. 문구는 가입 화면의 전문 보기 팝업과 같다 — `F-OFBCVL`
* 개인정보처리방침은 따로 두지 않고 개인정보 수집·이용 동의(BP 사업자 회원가입용, `PRIVACY_COLLECT`)를 연다. 로그인 화면 맨 아래 링크에서 다른 링크보다 굵게 두고 약관 전문 페이지 `/terms#PRIVACY_COLLECT` 로 간다(2026-10-19 재영) — 개인정보 보호법 제30조의 처리방침 공개 의무와 이용약관 본문의 「개인정보처리방침을 공개」 문구는 법무 확인이 필요하다 — `S-XJDKSI`
* 전문 표준안은 타사(시프티·flex·모두싸인·캐시노트·토스) 비교로 만들었다 — 이용약관은 7조에서 22조로 늘려 요금·데이터 소유권·개인정보 처리위탁·손해배상 한도·통지·관할을 채우고, 개인정보 동의는 항목·목적·기간·거부권 4단을 표로 쓰며, 마케팅 동의는 채널별 선택·2년 재확인·야간(21~08시) 별도 동의를 둔다 (2026-09-29).
* 개인정보 동의의 선택 항목은 따로 동의받지 않고 "입력한 경우에만 수집"으로 적는다 (2026-09-29). 이 방식이 개인정보보호법 제22조의 분리 동의 요건을 채우는지는 법무 확인을 기다린다.
* 아직 못 채운 값: 손해배상 한도 개월 수, 해지 후 데이터 내려받기 기간, 보안 로그 보관 기간, 문의 고객 보관 기간, 고객센터 연락처. 개인정보 처리위탁 계약(DPA)을 별도 문서로 둘지도 정하지 않았다.
