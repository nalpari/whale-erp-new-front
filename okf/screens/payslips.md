# api 로 그린다

목록은 `GET /payslips?month&status&storeIds&storeTypes&staffName&reviewPending&page&pageSize`, 상세는 `GET /payslips/:id` 다(`src/lib/payslips-api.ts`, 직원 목록
`staff-members-api.ts` 와 같은 `request()` · `authHeaders()` · `ApiError` 모양). 응답 타입은 `api-types.generated.ts` 의
`PayslipListResponseDto` · `PayslipDetailResponseDto` 를 그대로 쓴다. 메뉴 권한(MN000009 조회) · 관리 범위 · 가림은 api 가 본다.
상세의 없음 · 범위 밖 · 가림 · 이상한 id 는 404 → `notFound()`, 로그인 만료(401)는 `request()` 가 만료 안내 로그인 화면으로 보내고(2026-11-10), 그 밖의 api 오류(꺼짐 · 403)는 `error.tsx` 가 받는다.
화면 주소는 탭 BP 주소 `/bp/{bpCodeId}/payslips…` 다(`BP_PATH_SCREENS`, WHALEERP-637) — proxy 가 그 BP 를 `X-Bp-Code-Id` 로 실어 플랫폼 계정은
고른 BP 의 명세서만 본다. 쿼리 · 상세의 「목록」 주소(`payslipListHref`)는 옛 경로로 만들고 링크 · 이동에서만 탭 BP 를 붙인다 — 목록 표 · 상세(서버)는
`screenPath()`, 목록 조작 · 초안 팝업 · 검토 화면(클라이언트)은 `bpPath`, 초안 작성 뒤 이동(서버 액션)은 `bpHref`. 상세의 출퇴근 기록 · 근로계약 링크도
탭 BP 주소 화면이라 같이 씌운다. 목록이 api 거절(BP 를 고르지 않은 플랫폼 계정 400 · 다른 BP 403 · 없는 BP 404, `deniedMessageOf`)을 받으면 오류 화면이
아니라 그 문장을 보인다(근로계약 목록과 같다). 보통은 오지 않는다 — SessionGate 가 BP 없는 주소를 마지막으로 고른 BP 의 탭 BP 주소로 보내고, 고른 BP 가
없으면 플랫폼 탭으로 열어 「BP 를 먼저 선택해 주세요」로 막는다. 상세의 404(없는 BP 포함)는 그대로 찾을 수 없음이다.
상태 · 검토 사유 · 처리 구분 · 근로계약 상태 · 계약 유형 · 발송 채널 · 발송 결과 한글은 `getEnum` 으로 받는다(`PayslipStatus` ·
`PayslipReviewReason` · `PayslipLogType` · `ContractStatus` · `EmploymentType` · `PayslipDispatchChannel` · `DispatchResult`).

상세 오른쪽 단 맨 아래 「발송 이력」(WHALEERP-236)은 `dispatches` 를 채널마다 한 줄로 — 일시 · 채널(이메일 · 앱 푸시) · 결과(성공 파랑 ·
실패 빨강 배지), 처리 이력처럼 최근 것이 위다. 처리 이력의 「발송」 줄은 그대로 두고, 채널별 성공 · 실패는 이 표에서 따로 본다. 지금 api 는
이메일만 보내 줄을 남긴다 — 앱 푸시는 기기 토큰 · FCM 이 생기면(WHALEERP-241) 같은 표에 선다. 없으면 「발송 이력이 없습니다.」

# 목록은 Plane WHALEERP-233 을 따른다

칸과 필터는 Plane WHALEERP-233 완료 조건이 기준이고, 데모(`staff-sections.mjs` payList · payslipsFilter)와 **일부러 다르다**.

* 필터는 급여 기간(목록 위 달 이동) · 점포 · 직원명 · 명세서 상태 · 분류(검토 대기만, 아래)다(점포 · 직원명은 2026-10-19 사용자 요청으로 더했다).
  점포는 공통 점포 고르기(`StorePicker`)이고 **상단 점포 범위와 잇는다**(PR #88 공유, 2026-10-26 — 직원 목록과 같은 규칙): 목록에서 고른
  점포(`storeIds`) · 목록에서 비운 「전체」(빈 `storeIds=`) · 헤더 범위(`scope=ALL · DIRECT · FRANCHISE · STORE:id`) · 정해지지 않음(필터가
  헤더 범위로 채운다). api 에는 고른 점포 · 점포 하나 범위면 `storeIds`, 직영 · 가맹 범위면 `storeTypes`(그 유형의 폐점 점포는 api 가 뺀다)로
  보내고(`payslipStoreCondition`), 「확정 N건 발송」도 같은 조건이다. 주소의 범위를 이 탭에서 쓸 수 없으면 「전체」로 바꾸고 알린다. 예전
  점포명 주소(`?store=`)는 읽지 않고 상단 범위로 채운다. 직원명 검색칸은 `SearchField`(Enter · 돋보기, `staffName`). 직원명으로 거르면 본사 역할에게 가린 줄은 api 가 목록과 상태 건수에서 모두 뺀다 — 이름 검색으로 가린
  직원이 드러나지 않게. 상태 건수는 점포 · 직원명 필터를 따르고 상태 필터는 따르지 않는다.
  상태를 모두 고르면 `status` 를 빼고, 하나도 고르지 않으면 api 가 빈 값을 400 으로 막아 `status` 없이 부른 뒤 줄은 버리고
  상태 건수만 쓴다(0건).
* 칸은 순번 · 급여 기간 · 직원명 · 근무지 · 계약 유형 · 출퇴근 확인 여부 · 상태 · 발송일이다. 폭은 1260 창 기준 60 · 180 · 170 · 100(기준 폭, 왼쪽 정렬) · 90 · 130 · 150 · 70 이고, 넓은 창에서는 모든 열이 같은 비율로 늘며 표 최소 폭 950 을 넘치면 표 상자 안에서 민다(2026-11-18 사용자 지정). 필터는 초기화 조건(헤더 범위 · 지금 달)과 다르면 접기 버튼에 빨간 점(`FilterPanel` `applied`). 출퇴근 확인 여부는
  `isAttendanceConfirmed` — true 「확인」, false 「누락」, null(가린 줄) 「-」. api 에 누락 일수 칸이 없어 일수는 보이지 않는다.
  발송일은 `lastSentAt` 을 근로계약 목록처럼 MM-DD 로, 발송 전이면 「-」.
* 본사 근무지는 점포 선택지에서 「[본사] 상호」(`storeOptionLabel`)로, 목록 「근무지」 · 검토 화면 요약 띠 · 작성 팝업의 「점포」 칸에서는 이름 앞 [본사] 꼬리표(`StoreNameWithType` — 로그인 점포 목록에서 유형을 찾고, 없으면 api `storeIsHq`)로 보인다(2026-11-19).
* **검토 대기**(WHALEERP-234)는 상태가 아니라 분류다(운영 정책 PAY-01 · 06, 2026-10-26 재영 — STAFF-32 「목록 없음」을 바꿨다). 따로
  목록을 두지 않고, 검토 대기 사유(`pendingReviewReasons` — 출퇴근 누락 · 계약 만료 후 기록 · 기간 중 계약 변경 · 공제 미입력 · 확인 필요 기록
  포함, 공제 미입력은 api 가 공제 칸으로 판정한다)가 남은 줄의 상태 칸에 상태 배지 옆 「검토 대기」 꼬리표(공통 `Tag` — 표 머리 바탕 · 선 ·
  보조 글자색)를 붙인다. 「검토 중」 상태 배지(빨강)와 다른 모양이어야 해서 데모의 빨간 `p.tag("warn", "검토 대기")` 대신 DESIGN.md
  「분류를 말할 뿐 상태가 아니다」 꼬리표를 쓴다(운영 정책 v221 PAY-06, 2026-10-27 재영). 꼬리표에 마우스를 올리면
  사유 이름(`GET /enums` 의 `PayslipReviewReason`)이 보이고, 내용은 상세 「검토 대상 항목」에서 본다(걸린 사유만 — 걸리지 않은 사유를 「해당 없음」으로 보이던 「그 밖의 사유」 표는 2026-11-06 뺐다, 사용자 지정). 공제 미입력은 api 사유 행이 없어 상세가 저장된 공제 칸으로 판정해 「공제 미입력 · 빈 공제 이름」 줄을 더한다(`detailReviewReasons`, 작성 중 · 검토 중만, 재영 2026-10-28) — 임시저장 전 고친 칸은 금액 칸 아래 빨간 띠만 따라 바뀐다. 왼쪽 필터 맨 아래 「분류 · 검토 대기만」
  체크(주소 `reviewPending=true`, api 도 같은 이름 — 본사 역할에게 가린 줄은 api 가 뺀다). 건수 줄은 상태 넷 뒤에 11px 세로선을
  긋고 「검토 대기 N」 꼬리표를 따로 둔다(`reviewPendingCount`, 그 달 · 고른 점포(직원명이면 그 이름)) — 검토 대기는 작성 중 · 검토 중
  모두에 생기는 분류라 다섯째 상태처럼 「·」로 잇으면 합계가 맞지 않게 읽힌다(운영 정책 v221 PAY-06). 검토 대기 건수도 「검토 대기만」 목록처럼 본사 역할에게 가린 줄(본사 제공 동의 없는 가맹 직원)은 세지 않는다 — 둘의 차이로 가린 직원의 검토 대기(근태 이상 · 공제 미입력) 여부가 드러나지 않게(ATT-30, 운영 정책 v218, api PR #169 리뷰). 상태 · 직원명 · 검토 대기만 · 점포(고른 점포나 「전체」가 아닌 헤더 범위)로 거른 목록이 비면 「조건에 맞는 급여명세서가 없습니다.」(거르지 않았으면 「이 달의 급여명세서가 없습니다.」) — 점포만 골라 0건일 때 「이 달의 …」로 잘못 말하던 것을 고쳤다(리뷰 반영). 비어도 열 이름 줄은 두고 빈 칸이 목록 영역 남는 높이를 채운다(DataTable `fillEmpty`, 2026-11-05 사용자 지정, 3팀 확인 필요). 꼬리표에 화면 낭독기용 숨긴 사유 글자를 붙인다.
* 달 이동 아래 한 줄에 「총 N 건」 · 세로선 · 상태 넷 건수(「작성 중 3 · 검토 중 1 …」) · 세로선 · 「검토 대기 N」 꼬리표를 두고, 같은 줄 오른쪽 끝에 「확정 N건 발송」 · 건수 고르기를 둔다 — 모든 칸을 줄 가운데에 맞춘다(2026-11-05 사용자 지정, 3팀 확인 필요 — 전엔 상태 건수 줄과 공통 `ListToolbar` 의 「총 N 건」 줄이 따로 있었고, 아래 끝 맞춤이라 「총 N 건」이 처졌다).
* 상태 건수는 `statusCounts`(상태 필터와 상관없이 점포 · 직원명 필터만 건 그 달 건수, 직원명으로 거르면 가린 줄은 뺀다). 쪽 넘김은 `total` · `page` · `pageSize`,
  건수는 20 · 50 · 100(기본 20, URL 에서 뺀다). 명세서가 없으면 「이 달의 급여명세서가 없습니다.」
* 가린 줄(`isMasked`, 본사 제공 동의 없는 가맹 점포 직원, ATT-30)은 근무지 · 급여 기간 밖은 「-」, 직원명은
  「본사에 정보제공 미동의」(2026-11-05 사용자 지정, 3팀 확인 필요 — 전엔 「본사 제공 동의 없음」)이며 링크가 없다(payslipId 가 null 이라 순번으로 줄을 가른다).

# api 에 칸이 없어 뺀 것

목 시절 화면에 있던 값 가운데 api 응답에 없는 것은 값을 지어내지 않고 화면에서 뺐다.

* 목록 「계약 없음 · 초안 없음」 줄(이 달 명세서가 없는 재직 직원). 출퇴근 누락 일수는 상세의 경고 띠 설명에 api 사유 상세로 나온다
  (「출퇴근 기록이 등록되지 않은 날이 2일 있습니다(9월 5일 퇴근 미등록, …).」, WHALEERP-229).
* 상세 「급여 산정 기준」의 집계 근로시간 · 덧붙임 · 근무스케줄 기준 시간.
* 지급 칸 도움말의 계산 근거 글자(데모 「8.0h × 1.5배 · 가산 적용」) — 「계산값」 · 「계산값 A 을 B 으로 고침」만 남는다. 가산을 끈
  명세서의 연장수당은 앞에 「가산수당 미적용 · 1배로 계산」이 붙는다(PAY-05, 2026-10-26 재영). 가산 스위치를 바꾸면 토스트로 「임시저장하면 연장수당을 … 다시 계산합니다」를 알리고(상자 안에 띄우면 틀이 들썩였다, 2026-11-19 사용자 지정), 지금 칸 값이 저장된 금액과 다르거나 앞서 고쳐 둔 값이 있으면 「직접 고친 연장수당(N원)은 그대로 둡니다」를 붙인다(api 와 같은 기준 — 지금 칸 값으로 판단).
* 근로계약 번호(데모 `CTR-2026-0143`)는 contracts 에 칸이 없다. 내부 번호(`근로계약 #id`)는 고객이 찾을 수 없어 보이지 않고, 「근로계약」 줄은 「상태 · 근로계약 보기」 링크다(2026-11-06 사용자 지정, 3팀 확인 필요). 근로계약 급여액은
  고용형태와 상관없이 시급이라(2026-10-12) 「급여 산정 기준」 「통상시급 N 원」으로 보인다(2026-11-19 사용자 지정 — 전엔 「계약급여 N 원 / 시간」) — 월 기본시간 · 월간 연장은 api 응답에 칸이 없어 보이지 않는다. 근로계약 상태가 null 이면 「-」.

# 목록 「확정 N건 발송」 (WHALEERP-231 · 237)

확정 건이 있고 수정 권한이 있을 때 선다. 확인창 뒤 `POST /payslips/send`(server action `sendPayslips`)로 목록과 같은 달 · 점포 ·
직원명(`sendTargetOf` — 건수와 같은 조건)의 확정 명세서를 보낸다. 모두 보내면 토스트 「N건을 발송했습니다.」, 실패가 있으면 결과 창
「N건 발송, M건 실패」에 실패 대상(직원 · 이유)을 따로 보인다 — 가린 명세서는 이름 대신 「본사에 정보제공 미동의」. 끝나면 목록을
다시 받는다. 보내지 못한 명세서는 확정 그대로라 다시 보낼 수 있다.

# 검토 화면에서 고치기 · 확정 (WHALEERP-228 · 230)

버튼은 server action(`[payslipId]/actions.ts`)으로 api 를 부른다. 성공하면 토스트 뒤 `router.refresh()` 로 상세를 다시 받고,
page 가 `updatedAt` 을 `PayslipReview` 의 key 로 줘 금액 칸 · 스위치가 새 값으로 다시 선다. 실패하면 api 문장을 확인창 안에 보인다
(409 그사이 고침 · 상태 다름, 422 비어 있는 공제 등). api 가 `code` 를 붙인 5xx(메일 · 직원 앱 주소 설정 없음 503, 메일 실패 502)도
원인이 정해진 실패라 api 문장을 그대로 보인다. 그 밖의 5xx · 연결 실패 · server action 호출 끊김은 「결과를 확인하지 못했습니다」를
확인창에 두고 상세를 다시 받는다(실제로 저장 · 발송됐으면 새 값으로 다시 서며 안내도 사라진다). 목록 「확정 N건 발송」과 작성 팝업도
같은 규칙이고, 결과를 모르면 목록을 다시 받는다 — 오류 화면으로 가지 않아 입력하던 값이 남는다.

* **임시저장**(`PUT /payslips/:id`) — 줄마다 급여 항목 id 와 금액(빈 칸 null — 0 과 다르다), 가산 · 3.3% 스위치, 상세의 `updatedAt`.
  금액 칸은 숫자와 쉼표만 받는다(화면 설계 공통 기준 1번 · WHALEERP-633) — 붙여 넣은 「원」 · 「₩」 · 공백은 떼고, 그 밖의 글자(소수점 · 빼기 등)가 섞인 입력은 통째로 받지 않는다(글자만 지우면 다른 금액이 된다). 그래도 숫자가 아닌 칸이 있으면 보내지 않고 그 이름을 알린다. 상태는 그대로다. 3.3% 는 파트타이머만 보낸다.
* **항목 추가** — 확인창 「공제 항목 추가」([닫기] · [추가])는 `GET /payslips/additional-items`(추가 공제)를 체크 목록으로 보이고, 체크한 것을 한꺼번에 빈 칸으로 붙인다. 붙여도 창은 닫히지 않고 붙은 항목은 체크 · 잠금 + 「추가됨」으로 남는다 — [닫기]로만 닫는다(2026-11-19 사용자 지정, 전엔 드롭다운으로 하나씩 · 붙일 때마다 닫힘). 붙인 추가 공제는
  항목 이름 줄 오른쪽 끝 「빼기」로 뗀다. 둘 다 임시저장해야 남는다(api 는 실은 추가 공제가 곧 붙은 목록이다).
* **지난 명세서에서 불러오기**(`GET /payslips/:id/previous-values`) — 같은 직원의 지난 명세서의 공제와 직접 넣는 지급 값을 칸에 채운다
  (`applyPrevious` — 같은 급여 항목 칸은 바꾸고, 없는 추가 공제는 붙이고, 이 명세서에 없는 지급 · 기본 공제 줄은 버린다). 저장하지
  않고 위에 「… 값 N칸을 불러왔습니다. 임시저장해야 남습니다.」 띠를 둔다. 지난 명세서가 없으면 확인창을 닫고 토스트 「불러올 지난 명세서가 없습니다.」로 알린다(WHALEERP-689). 확인창 안내는 「해당 직원의 지난 급여명세서에서 공제 내역과 직접 입력한 지급 항목 금액을 불러옵니다. 불러온 내용은 임시저장해야 최종 반영됩니다.」.
* **확정**(`POST /payslips/:id/confirm`) — 저장하지 않은 바뀜이 있거나 보이는 공제가 비어 있으면 확인창의 확인이 막힌다(api 도
  422 `DEDUCTION_MISSING` 로 막는다). 상세의 `confirmableFrom`(확정할 수 있는 첫날) 전이면 머리의 [확정]을 막고 요약 띠 상태 칸에 「YYYY-MM-DD부터
  확정할 수 있습니다.」를 둔다(2026-11-19 사용자 지정 — 전엔 버튼 아래)(`confirmBlockedUntil`, 오늘은 page 가 서버에서 정한 한국 날짜 — api 도 422 `PERIOD_NOT_ENDED` 로 막는다, WHALEERP-690).
  막혀 있으면 브라우저의 한국 날짜가 확정 가능일에 닿았을 때(그날 자정 · 볼 때가 지난 뒤 화면 · 창으로 돌아왔을 때)만 `router.refresh()` 로 다시 받아, 열어 둔 채
  그날이 와도 풀린다(`blockedRecheck`). 받았는데도 막혀 있으면(PC 시계가 빠름) 1분에서 두 배씩 늘려 30분 간격까지 다시 보고(`nextRecheckMs`),
  돌아왔을 때는 볼 때가 지났으면(잠자기로 타이머가 밀림) 바로 본다(간격은 그대로, 처음 열 때는 받지 않는다). 저장하지 않은 입력이 있으면 미룬다. 검토 사유가 있으면 「확인한 것으로 남고, 확정 취소하면 다시 검토 대기가 됩니다」를 덧붙인다.
* **확정 취소**(`POST /payslips/:id/cancel-confirmation`) — 확정 · 발송 완료에서 검토 중으로. 확정이 확인한 검토 사유가 다시 확인 전이
  되어 검토 대기로 돌아간다(api, 운영 정책 v221 PAY-06). 발송 완료에서 취소하면 확인창이
  「직원 근무 앱에는 다시 보낼 때까지 「검토 중」으로 금액 없이 보인다」고 알린다(api 의 `correcting`, 2026-10-21 사용자 결정).
* **발송**(`POST /payslips/:id/send`, 확정일 때) · **재발송**(`POST /payslips/:id/resend`, 발송 완료일 때) — 머리 버튼, 확인창을 거친다.
  직원 앱 계정 이메일로 간다. 메일 설정 없음 · 계정 없음 · 메일 실패 등은 api 문장을 확인창에 보인다(실패하면 확정 그대로).
* 화면 제목은 목록과 같은 「급여명세서 관리」다(다른 메뉴 상세처럼 메뉴 이름, 사용자 결정). 머리 버튼은 [임시저장] [확정](확정 · 발송 완료면 [확정 취소] [발송]/[재발송]) 다음 맨 오른쪽에 [목록]을 둔다(직원 · 근로계약 · TO-DO 상세와 같게). 「미리보기」 창 제목은 「급여명세서 미리보기」.
* 위쪽 경고 띠(`reviewBand`)는 이미 확인한 검토 사유(`acknowledgedAt` — 확정 때 확인됨)를 세우지 않는다.
* 3.3% 원천징수 칸 아래는 셈식 「지급 합계(비과세 포함) N원 × 3%」(지방소득세 칸은 × 0.3%)다 — 사업소득에는 비과세가 없다. 금액은 관리자가 넣는다(PAY-03, 2026-11-19 사용자 지정).
* **배치(2026-11-19 사용자 지정, DESIGN.md 「상세 화면 틀」):** 제목 줄(「급여명세서 상세」 + 버튼) 아래 요약 띠 「성명 · 고용형태 · 급여월 · 근무지(유형 꼬리표) · 상태」, 경고 띠 「⚠ 검토가 필요한 사유가 N건 있습니다. 오른쪽 검토 사유를 확인하고, 문제가 없으면 [확정]해 주세요.」(공제 미입력뿐이면 없음). 왼쪽 7 : 오른쪽 5.
  왼쪽 묶음은 「지급 항목」(도구 줄: 「연장·야간·휴일 가산수당 적용(5인 이상 사업장 필수)」 스위치 + 도움말(상시근로자 5명 이상 의무 · 4명 이하 선택 · 대표자 제외 1개월 평균) · [출퇴근 다시 불러오기]) · 「지급 항목(비과세)」 · 「공제 항목(4대보험 · 세금)」(도구 줄: 파트타이머만 「3.3% 원천징수 적용」 · [지난 명세서에서 불러오기]. 스위치를 켰는데 4대보험 가입 여부 둘 중 하나라도 true 면 스위치 아래 느낌표 안내 「4대보험에 가입한 직원은 근로소득자라 보통 3.3% 원천징수 대상이 아닙니다. 세무 담당자와 확인해 주세요.」(공통 `GuideNote`, `withholdingNeedsCheck` — 확정은 막지 않는다, WHALEERP-756)) · 「공제 항목(추가)」([항목 추가]) — 제목 줄 오른쪽 「합계 N원」, 금액 칸은 한 줄 세 칸. 맨 아래 합계 띠 「지급 항목 합계 − 공제 항목 합계 = 실지급액」. 공제 칸은 국민연금 · 건강보험 · 장기요양보험 · 고용보험 · 소득세 · 지방소득세(3.3% 는 끝) 순서로 보인다(`sortDeductions` — api 순서와 다르다, 「공제 미입력」 사유 글자도 같은 순서).
  오른쪽 확인 상자는 「검토 사유」(건수 빨강, 사유마다 이름 600 · 점선 링크 「출퇴근 기록 보기 ›」 · 「공제 칸으로 이동 ›」 · 「근로계약 보기 ›」 · 아래 회색 상세) · 「급여 산정 기준」(산정기간 + 「출퇴근 기록 보기 ›」 · 출퇴근기간(다를 때만) · 통상시급 · 근로계약 상태 + 「근로계약 보기 ›」) · 「급여명세서 수정 및 처리내역」(줄마다 api 요약 글자 두 줄까지 · 더보기, 오른쪽 「처리자 | 일시」) · 「발송 이력」.
* **출퇴근 다시 불러오기**(`POST /payslips/:id/recalculate`, 작성 중 · 검토 중) — 확인창을 거쳐 기본급 · 주휴수당 · 연장수당을 지금
  출퇴근 기록으로 다시 채운다. 세 칸에서 고친 값과 임시저장하지 않은 변경은 사라진다(확인창이 「(급여 기간) 출퇴근 기록으로 기본급·주휴수당·연장수당이 재계산되며, 세 칸에서 직접 고친 값과 임시저장하지 않은 내용은 초기화됩니다.」로 알린다). 계산은 api 가 한다(WHALEERP-227,
  api okf 「지급 항목 계산」). 가산 스위치는 칸을 건드리지 않는다 — 임시저장 때 api 가 그 값으로 다시 계산하고, 고치지 않은 칸은
  새 계산값을 따른다. 앱 푸시는 api 에 없어 보내지 않는다.

금액은 `adjustedAmount ?? calculatedAmount`(넣지 않았으면 빈 칸), 3.3% 를 켜면(공제 항목 상자의 「3.3% 원천징수 적용」) 소득세 · 지방소득세 칸이 빠지고 사업소득세(3%) ·
지방소득세(0.3%)가 선다 — 4대보험 줄은 3.3% 와 관계없이 근로계약서의 가입 체크대로 보인다(WHALEERP-756, 2026-11-20 김지영): 건강보험 · 국민연금이면
국민연금 · 건강보험 · 장기요양보험, 고용보험 · 산재보험이면 고용보험. 미가입 보험 줄은 **저장된 금액이 비었거나 0 원일 때만** 숨는다 — 예전엔 4대보험을
모두 채워야 확정돼 0 아닌 금액이 든 명세서가 있어, 숨기면 저장된 합계와 보이는 줄이 어긋나고 줄이 없어 지울 수도 없었다(2026-11-24 사용자 결정).
숨는지는 api 가 준 줄(저장된 값)로 판정해 입력 중에 칸을 0 으로 지워도 줄이 사라지지 않고, 0 으로 저장하면 다음 화면에서 숨는다. 「지난 명세서에서
불러오기」는 미가입이라 숨은 4대보험 줄은 채우지 않는다(저장 뒤 줄이 갑자기 나타나지 않게). 가입 여부는 api 상세의
`isHealthPensionInsured` · `isEmploymentInjuryInsured`(급여 기간에 효력이 있던 계약 중 하나라도 체크했으면 true — api okf 「4대보험 가입 여부」)이고,
저장하지 않고 api 가 읽을 때 계약으로 센다 — 바로잡기 · 서면 계약 등록으로 같은 기간 계약이 생기면 바뀔 수 있으나 0 아닌 금액 줄은 늘 보여 합계는
어긋나지 않는다. 바로잡기로 닫힌 이전 계약(ENDED)도 기간에 걸리면 가입으로 남는다. 숨은 줄은 합계 · 빈 칸(확정 막기) · 「공제 미입력」 사유 ·
[공제 칸으로 이동]에서도 세지 않는다(`isItemShown`, [직원 운영 관리](/staff.md) 급여). 고칠 수 있는 것은 작성 중 · 검토 중이고 「급여명세서 관리」
(MN000009) 수정 권한이 있을 때뿐이다. 확정 · 발송 완료는 읽기만 하고 「확정 취소」와 「발송」 · 「재발송」을 둔다(확정 취소는 데모에 없는 버튼). 경고 띠의 「출퇴근 기록 확인」과
「출퇴근 기록 보기」는 출·퇴근 현황 조회를 그 점포 · 직원으로, 아래 목록을 급여 기간 첫 주 월요일부터 끝까지의 그 직원 기록 전체(`fixAll`)로 연다(`attendanceHref`, WHALEERP-664 — 보정 대상만 보이면 경고 띠의 날짜를 찾지 못해서).

# 급여명세서 작성 (WHALEERP-226)

화면명 오른쪽의 「급여명세서 작성」(기본 버튼, 근로계약 관리 「계약서 작성」과 같은 자리 · WHALEERP-632, MN000009 등록 권한일 때만 보임)은 화면을 옮기지 않고 **목록 위 팝업**(720px, 데모 `staff-sections.mjs`
`pickId`)을 연다. 달은 목록의 달이다. **미리 고른 직원은 없다**(데모처럼 특정 직원 명세서로 바로 가지 않는다). 따로 있던
`/payslips/new` 화면은 지웠다.

* 열 때마다 `GET /payslips/candidates?month=` 를 server action(`getPayslipCandidatesAction`)으로 받는다. 위에 점포 선택(「전체 점포」 +
  작성 대상의 점포)과 직원 이름 검색칸이 있고, 표를 화면 안에서 좁힌다. 본사 역할에게 동의 없는 가맹 점포 직원은 api 가 빼서 없다.
* 표: 선택(라디오) · 직원 · 점포 · 계약 유형 · 근로계약(유효 / 「계약 없음」 빨간 꼬리표) · 명세서(미작성 / 「작성됨」 회색 꼬리표).
  근로계약이 없거나 이미 작성된 직원은 라디오가 막힌다. 고를 수 있는 직원에게 출퇴근 기록이 없으면 이름 옆에 「출퇴근 누락」을
  작게 붙인다. 작성 대상이 아예 없으면(근로계약이 없거나 모두 작성함) 「급여명세서를 작성할 직원이 없습니다.」, 점포 · 이름으로 좁혀서 0줄이면 「조건에 맞는 직원이 없습니다.」(2026-11-05 사용자 지정, 3팀 확인 필요).
* 머리: 제목 「급여명세서 작성」 옆에 달 꼬리표(「2026년 11월」 — 연한 포인트 바탕 · 포인트 파랑 16px 600 · 28px · 알약형, DESIGN.md 포인트 파랑 예외), 그 아래 13px 회색 안내 「근로계약이 체결된 직원 중 급여명세서를 작성하지 않은 직원을 선택해 주세요.」. 제목 · 달 · 안내를 한 묶음(6px)으로 두고 입력칸과는 18px 뗀다 — 어느 달 명세서인지가 이 팝업의 핵심이라 달을 꼬리표로 보이고, 문구에서는 「이 달」을 뺐다(「이번 달」로 읽혔다, 2026-11-05 사용자 지정, 3팀 확인 필요).
* 직원 표는 직원 130 · 점포 160(긴 점포명은 말줄임) · 표 최소 640px — 좁은 팝업에서 열이 뭉개지지 않게(2026-11-19 사용자 지정).
* 아래 오른쪽 취소 · 작성(고르기 전에는 막힘). 작성은 `createPayslip`(`POST /payslips`) → 토스트 「급여명세서를 작성했습니다.」 뒤 그 검토 화면으로 간다(action 이 주소를 돌려준다,
  WHALEERP-688 — 일괄 작성처럼 결과를 알린다). 409 는 문장과
  「작성된 명세서 보기」 링크, 422 · 404 등은 문장을 팝업 안에 보인다.
* 아래 왼쪽 「일괄 작성」(달은 제목 옆 꼬리표가 말하므로 「이 달」을 뺐다, 2026-11-05 사용자 지정, 3팀 확인 필요) — 확인창(만들 건수) 뒤 `bulkCreatePayslips`(`POST /payslips/bulk`), 결과를 토스트 한 줄
  (「2건 작성 (출퇴근 누락 1건) · 3건 건너뜀 (이미 있음 1 · 계약 없음 2)」, `bulkSummary`)로 띄우고 팝업을 닫은 뒤 목록을 다시 받는다.
  만들 줄이 없으면 막힌다. 확인창은 팝업 `<dialog>` 밖에 둔다 — 안에 두면 확인창의 Esc 가 React 트리를 따라 팝업까지 닫는다.
* 닫으면(취소 · Esc) 고른 직원 · 좁히기 · 오류를 지운다. 공통 컴포넌트에 큰 팝업이 없어 확인창 · 변경 이력 팝업과 같은 네이티브
  `<dialog>` 를 쓴다.
* 초안은 작성 중 상태다. 기본급 · 주휴수당 · 연장수당은 api 가 계산해 채우고(WHALEERP-227), 나머지는 비어 있다.
