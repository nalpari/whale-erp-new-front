ERP·플랫폼 레이아웃을 따로 두지 않는다(2026-10-14) — 틀(`src/components/site/admin-frame.tsx`)이 같고, 다른 것은 탭의 서비스로 가른다. 틀 안의 `SessionGate`(`session-gate.tsx`)가 로그인 정보와 이 탭의 서비스·BP·점포·공통코드를 준비할 때까지 로딩 화면을 보이고, 준비되면 `AdminHeader`(`admin-header.tsx`)와 본문을 그린다. 탭의 서비스(`WHALE_ERP`·`PLATFORM`)는 sessionStorage `current-bp` 에 BP 와 함께 둔다 — BP·가맹 계정은 늘 ERP, 플랫폼 계정은 자기 BP 탭이 플랫폼이고 고른 BP 로 연 탭이 ERP 다. 고르기는 헤더 서비스 바로가기의 웨일ERP 다 — 플랫폼 계정이 누르면 BP 선택 팝업(`bp-select-dialog.tsx`, `GET /bp-codes`: 사용·미사용·탈퇴 포함, 삭제·플랫폼 BP 제외 — api #72)이 열리고, ERP 탭에서 눌러도 다시 열린다. 고르면 새 탭(noopener)으로 BP 이동 화면 `/bp-switch?bp=&bpCode=` 를 연다(주소는 `bpSwitchUrl` 로 만들고 `bpOfSwitchUrl` 로 읽는다). 주소는 id 만 믿는다 — 새 탭이 `bpCode` 로 `GET /bp-codes` 를 찾아 id 가 같은 줄의 상호·코드를 쓰고, 못 찾거나 볼 수 없으면 안내하고 플랫폼으로 연다. 고른 BP 를 주소로 넘기는 것은 탭들이 같이 쓰는 `selected-bp` 가 새 탭이 준비되는 사이 다른 탭의 선택으로 바뀔 수 있어서다. 그 탭의 `SessionGate` 가 로딩 화면에 「BP 로 이동하는 중입니다」, 서버에서 BP 를 확인하면 「상호(BP코드) · 전체 점포로 여는 중입니다」를 보이며(적용 안내를 토스트 대신 로딩 화면 문구로 한다) 고른 BP 의 점포·공통코드를 새로 받아 탭 sessionStorage(`current-bp`·`stores`·`codes`, `scope` 는 전체)를 채우고, 받은 뒤에 `selected-bp` 에 적은 다음 그 서비스 홈으로 `replace` 한다(받기가 실패하면 앞서 고른 BP 가 남는다). `?bp=` 는 이 화면의 것만 본다. 이동 주소에서 BP 를 읽지 못하면 조용히 넘어가지 않고 안내한다. 플랫폼관리 바로가기는 ERP 탭이면 그 탭은 두고 플랫폼(`/platform`)을 새 탭(noopener)으로 연다 — 같은 탭을 플랫폼으로 바꾸면 앞서 본 ERP 화면이 뒤로 가기 기록에 남아 뒤로 갈 때마다 「접근 권한이 없는 메뉴」로 막혔다. 계정·메뉴(localStorage)는 바꾸지 않는다. 브라우저 탭 제목에는 BP 상호를 붙이지 않는다 — 즐겨찾기 이름에 상호가 남아, 나중에 그 즐겨찾기가 마지막으로 고른 다른 BP 로 열리면 헷갈린다(2026-10-20 재영). 직원·계약 등 업무 화면의 데이터는 아직 고른 BP 를 따르지 않는다(서버 컴포넌트가 탭 값을 못 봄 · api WHALEERP-301, 2026-10-19 A안). 탭 값이 없는 새 탭은 주소가 속한 메뉴의 서비스로 정한다(`resolveTab`, `serviceOfPath`). 헤더 메뉴는 그 서비스의 메뉴(`serviceCode`)만 2단계까지(조회 권한이 없는 메뉴는 권한 있는 첫 하위 메뉴로 연결하고, 갈 곳이 없으면 빼며, 오른쪽 사용자 칸은 이름만 보인다 — 권한 이름은 2026-10-20 뺐다), 오른쪽 선택기는 ERP 면 점포 범위다(플랫폼 탭의 BP 선택기는 아직 없다). 범위를 바꾸면 지금 화면 메뉴(목록 · 상세 · 등록 · 수정, `usePageMenu`)의 목록으로 늘 가고 다른 검색 조건은 초기값이다(메뉴가 아닌 화면은 범위만 바뀐다, 2026-10-21 정책). 범위는 탭 안(sessionStorage)에만 있어 서버가 모르므로, 헤더가 메뉴로 갈 때(범위 변경 · 메뉴 링크) 짧은 값 하나 `?scope=ALL · DIRECT · FRANCHISE · STORE:12` 로 싣는다(`src/lib/store-scope.ts` 의 `withScope` — 메뉴 링크 · 범위 변경 모두 전체도 `scope=ALL` 로 적는다). 점포 번호는 1~9자리 양의 정수만 받는다. 어느 메뉴에 점포 검색 필터가 있는지 헤더는 모른다 — 메뉴 주소 · 코드는 환경마다 바뀔 수 있어 적어 두지 않는다. 필터가 있는 목록만 서버에서 `scope` 를 읽어 api 조건으로 바꾸고(직영 · 가맹 전체는 점포를 풀지 않고 점포유형으로, 점포 하나는 그 id), 없는 목록은 모르는 값이라 무시한다. 목록에서 사용자가 고른 점포는 그 목록 주소의 `storeIds` 에 두고 `scope` 보다 앞선다(목록에서 비운 「전체」는 빈 `storeIds=` — 쿼리 객체의 `storesCleared`). 헤더가 실어 온 전체(`scope=ALL`)와 목록에서 비운 전체는 다른 값이라, 헤더의 전체는 목록을 조작해도 `scope=ALL` 로 남아 뒤로 가기에 헤더가 따라온다. `scope` 는 늘 헤더 범위만 뜻해서, 주소에 `scope` 가 있으면 그 탭의 헤더 범위도 그 값으로 맞춘다(`admin-header.tsx` 의 `ScopeFromAddress` — 다른 탭에서 복사한 주소를 열 때. 그 탭의 점포에 없는 범위는 따르지 않는다). 상세 · 등록 · 수정을 오갈 때는 목록 주소를 `?back=` 으로 넘겨 그대로 돌아오고, 다른 메뉴로 갔다 헤더로 다시 들어오면 범위를 따른다. 점포 조건이 주소에 없으면(주소 직접 입력 · 즐겨찾기 · 그런 주소로 뒤로 가기) 필터가 범위로 채워 다시 검색한다. 전체도 `scope=ALL` 로 적으므로 헤더를 거친 기록 항목마다 범위가 남아, 뒤로 · 앞으로 가기에도 헤더가 주소를 따라온다(`scopeFromAddress`) — 전체를 빼던 때는 「전체로 메뉴에 들어옴 → 직영 → 뒤로」에서 헤더가 직영에 남고 필터가 다시 직영으로 채웠다. 서버가 고른 점포를 빼면 필터 칩도 서버 값으로 돌아오고(칩 동기화 키에 요청한 점포를 넣는다), 뺀 점포는 점포 고르기 후보에서 숨긴다(`droppedStoreIds` · `StorePicker` 의 `hidden` — 다시 고르면 같은 주소로 가 칩이 어긋난다). 필터가 다시 채울지는 주소에 점포 조건이 있는지로만 정한다 — 헤더 범위 변경에 반응하면 헤더의 이동을 덮는다. 범위의 점포 하나를 서버가 api 로 찾지 못하면 「전체」로 보고 「상단에서 고른 점포를 찾을 수 없어」로 안내하고(`keepFoundStores` · `resolveStoresQuery`), 주소의 범위를 그 탭에서 쓸 수 없으면(고를 점포가 없다 — `isUnusableScope`) 헤더는 따르지 않고 필터가 「전체」로 바꿔 토스트로 알린다. 헤더 범위(직영 · 가맹)와 고른 점포유형이 겹치지 않으면 빈 목록 · 엑셀 400 이 그 이유로 알린다(`scopeTypeMismatch`). 점포 조건 · 점포상태는 전용 함수(`withPickedStores` · `withScopeCondition` · `withStatuses`)로만 바꾸고 `withStoreFilter` 는 그 밖의 조건만 받는다. 직영 · 가맹 범위의 칩은 로그인 정보의 점포(폐점 제외)로 그리고 api 는 점포유형으로 거르므로, 로그인 뒤 생긴 점포나 「폐점」을 켰을 때의 폐점 점포는 목록에만 나온다(받아들인 차이). 등록 · 삭제 뒤 돌아갈 목록은 `withoutStoreSearch`(빈 `storeIds=` — 헤더 범위는 바꾸지 않는다)다. 탭 sessionStorage 의 `store-picks`(목록에서 고른 점포 기억)는 2026-10-21 에 없앴고 키는 로그아웃할 때 지우려고만 남겼다. 그 서비스의 홈이 아니고 그 서비스 메뉴에 없는 주소면 안내 후 `history.back()`(기록이 없으면 홈)이다 — 플랫폼 탭에서 ERP 주소로 왔으면(마지막으로 고른 BP 없이 즐겨찾기·주소 입력) 권한 없음 대신 「웨일ERP 바로가기에서 BP 를 먼저 골라 주세요」라고 안내한다(강제 BP 선택 팝업은 두지 않는다) — BP 계정이 플랫폼 주소에 오거나 플랫폼 탭에서 ERP 주소를 치면 여기서 막힌다. 훅 `useAccount`·`useService`·`useMenus`·`useScope`·`useMenuRole`·`usePagePermission`(지금 주소의 메뉴 권한 — 메뉴 코드 없이 `menuOfPath` 로 찾는다. 화면이 열리는 판정 `isAllowed` 와 같은 메뉴, 여럿이 맞으면 url 이 가장 긴 것)·`useStores`·`useCodes`·`useCurrentBp` 로 화면이 읽는다. 로그인 없이 열리는 곳은 공개 경로 목록뿐이고(`src/lib/auth-routes.ts` 의 `isPublicPath` — 모르는 경로는 막는 쪽), 로그인하면 권한 유형 PM·PA 는 `/platform`, 그 밖은 `/home` 으로 간다(`homeOf`). GlobalHeader 로고는 아직 `/` 로 걸려 있다(로그인한 채 누르면 proxy 가 자기 홈으로 보낸다, #289).
* `src/proxy.ts` - 쿠키만 보는 낙관적 확인. 공개 경로(`isPublicPath`)가 아닌데 세션이 없으면 쿠키를 지우고 `/login`, 접근 토큰을 받은 지 10분이 지났으면(만료 50분 전부터) `POST /auth/admin/refresh`(5초 제한)로 쿠키를 새로 굽고(401 이면 쿠키를 지우고 `/login`, 그 밖의 실패는 접근 토큰이 아직 안 끝났으면 현재 쿠키로 계속하고 끝났으면 `/login`) — api 세션이 갱신 때만 연장되므로, 일찍 갱신해야 「마지막 사용부터 1시간」대로 쓰는 동안 끊기지 않는다. 서버 액션 요청(`next-action` 헤더)은 갱신하지 않는다(로그아웃의 쿠키 삭제와 겹치지 않게) —, 로그인한 채 `/`(로그인 전 홈, #289) · `/login` · `/find` 를 GET 으로 열면 자기 홈으로 보낸다(`redirectsSignedIn`, auth-routes.ts). `/` 는 접근 토큰이 살아 있을 때만이다 — 1시간 넘게 쉬어 끝난 로그인의 쿠키로 홈을 보러 오면 로그인 화면이 아니라 로그인 전 홈을 그대로 보인다. 다른 로그인 전 화면((site))은 머리말의 「홈으로」를 두고 그대로 보인다. 탭 BP 주소 `/bp/{bpCodeId}/...` 는 요청 헤더 `x-bp-code-id` 를 붙여 옛 경로(폴더)로 rewrite 하고, 들어온 `x-bp-code-id` 는 늘 지운다(BFF `/api/*` 만 브라우저가 실은 값을 숫자일 때 남긴다). BP·가맹 계정이 남의 BP 주소로 오면 세션 쿠키의 `bpCodeId` 로 `/bp/{소속}/...` 에 307 한다(GET 만 — 서버 액션 POST 는 보내지 않는다). 먼저 보고, 통과하면 서버 액션 `verifyBusiness` 가 api `POST /auth/signup/business-verifications` 를 부른다 — api 가 번호 중복 → 국세청 진위확인을 하고 10분짜리 토큰을 준다. 확인하는 동안은 세 칸·버튼과 가입 버튼이 잠긴다. 토큰과 받은 시각은 화면 상태에만 두고, 가입할 때 `bizVerificationToken` 으로 싣는다. 세 칸이 비어 있으면 사업자정보 없이 가입하지만, 값이 있는데 인증이 없으면(재인증 · 10분 경과 · 가입 거절로 풀린 뒤 포함) 가입 요청을 보내지 않고 「인증하기를 눌러 사업자정보를 확인해 주세요.」를 띄운다(10분 경과는 「사업자정보 인증이 만료되었습니다. 다시 인증해 주세요.」)(`bizSubmitBlock`) — 보이던 사업자정보가 조용히 빠진 채 가입되지 않게(PR #30 ⑤ 블로커). 받은 지 10분이 지났으면 가입 요청을 보내지 않고 인증을 풀어 다시 인증하게 하고, api 가 가입을 토큰 만료(400)나 사업자번호 중복(409)으로 거절해도 그 문구로 가려(`isBizSignupRejection`) 인증을 풀고 사업자정보 칸에 보인다. 진위확인 실패는 네 화면 공통 문구(`lib/biz-verification-rules.ts` 의 BIZ_MESSAGE)로 보인다 — 409 중복은 번호 칸 아래, 422 불일치 · 503 장애(로그) · 429 한도(일반 문구 「잠시 후 다시 시도해 주세요.」, 로그) · 그 밖은 인증하기 버튼 위 한 줄, 400 만 api 문구 그대로다(`biz-verification.ts`, 2026-10-22). 불일치는 어느 칸이 틀렸는지 몰라 칸 테두리를 빨갛게 하지 않는다. 기본정보 칸은 아이디|이름, 비밀번호|확인, 이메일|연락처, 상호명 순이다(2026-10-13). 가입 완료 화면의 상호명·아이디·이메일은 가입 성공 뒤 서버 액션이 심는 httpOnly 쿠키(`signup-done-cookie.ts`, 10분, 경로는 `SIGNUP_DONE_PATH` 상수 `/signup/done`)로 받는다 — 쿠키가 없거나 깨졌으면 로그인으로 보낸다(명세 `S-UUBGOD`). 서버 액션은 사용자 IP 를 `X-Forwarded-For` 로 api 에 넘긴다 — api 의 IP 한도(가입은 도입문의와 같이 IP 당 1시간 5건)가 방문자별로 세어지려면 api `TRUST_PROXY` 에 이 서버가 있어야 하고, Next 앞에 `X-Forwarded-For` 를 덧붙이거나 덮어쓰는 프록시가 있어야 한다 — Next 는 이 머리말이 이미 있으면 그대로 두므로, 바로 노출되면 브라우저가 지어 보낸 IP 가 api 까지 간다. api 실패는(사업자정보 거절 400 · 409 는 위처럼 따로) 400 · 409 만 api 문구를 그대로 보이고 그 밖(429 · 404 · 5XX)은 정해진 문구로 보이며 서버 로그에 남긴다(`api-failure.ts`). 409 를 받으면 아이디 · 이메일을 다시 확인해 걸린 칸에 오류를 띄우고, 응답을 받았는지 알 수 없는 실패(10초 시간 초과 · 서버 액션 전송 실패)와 api 가 받은 뒤의 실패(응답 모양 · 완료 쿠키)는 「이미 가입되었을 수 있으니 로그인을 먼저 시도해 주세요」로 안내한다. 「웨일ERP 시작하기」는 비밀번호 없이 로그인한다(명세 [Auth](/auth.md)) — 서버 액션 `startSessionFromSignup` 이 완료 쿠키의 `signupToken`(10분, 폼에 싣지 않고 쿠키에서 읽자마자 지운다)으로 api `POST /auth/admin/signup-session` 을 불러 세션 쿠키를 굽고 권한 유형별 홈(`homeOf`)으로 간다. 이미 다른 계정으로 로그인돼 있으면 그 세션을 api 에서도 로그아웃한다. 토큰이 없거나(10분 경과 · 재사용) 거절되면 세션 쿠키까지 지우고 `/login` 으로 보낸다 — 남은 세션이 있으면 proxy 가 `/login` 을 옛 계정 홈으로 돌려보내기 때문이다. 완료 화면의 「로그인 화면」 글자 링크와 가입 화면의 「이미 계정이 있나요? 로그인」은 세션이 없으면 `/login`, 다른 계정 세션이 남아 있으면 그 계정의 홈으로 건다(머리말의 「홈으로」와 같은 이유). 관리자 웹 로그인은 아이디의 대소문자를 구분하고 api 는 가입 아이디를 소문자로 저장하므로, 아이디 칸은 입력하는 순간 소문자로 바꿔 보인다(`normalizeLoginId`) — 대문자로 친 그대로 두면 가입한 아이디를 그대로 쳐서는 로그인할 수 없다(PR #23 ⑤ 블로커). `(site)` 틀 전체가 `design/guest` 의 `GuestHeader`·`GuestFooter` 를 쓰고, 홈·`/login` 본문도 guest 디자인으로 바꿔 더는 두 디자인 시스템이 섞이지 않는다(2026-10-19 — 그 전의 `SiteNav`·`SiteFooter` 는 지웠다). 로그인한 채 열면 머리말의 Login 자리에 「홈으로」(자기 홈, `homeOf`)를 보인다 — `(site)/layout.tsx` 가 세션을 읽어 `GuestHeader` 에 넘기고, 디자인 샘플은 늘 Login 이다(main 의 PR #44 를 병합 때 옮김). 1720px 최소폭도 틀이 건다. 약관동의의 「내용보기」 팝업(`terms-dialog.tsx`)은 처음 열 때 api 시행 중 약관(`TERMS_SERVICE` · `PRIVACY_COLLECT`)을 받아 `TermsMarkdown` 으로 그린다 — 화면에 보인 버전과 동의 기록 버전이 같다. 목업 문구 사본(지운 파일)과 미정 값(`[ ]`) 빨간 표시는 지웠다(2026-10-19). 다른 화면(`stores`·`staff-members`)과 달리 이 폴더에만 있던 `_components/` 하위 폴더를 걷어 모든 파일을 `signup/` 바로 아래로 평평하게 옮겼다(2026-10-19) — 나머지 화면 폴더 전부가 하위 묶음 없이 평평한 구조다. 사용자 * `src/app/(public)/(site)/leads/` · `src/lib/leads.ts` - 비로그인 도입문의 `/leads`(#297 · #298, S-SDMDKC). 라우트 이름은 네이밍 규칙의 도입문의 자원 `lead` 를 따른다(데모 · 샘플은 `inquiry`). 머리말 · 화면마다의 「도입문의」 링크(`guest-routes.ts` 의 `SITE_ROUTES.leads`)와 공개 경로(`auth-routes.ts`)도 `/leads` 다. 폼은 디자인 샘플과 같은 `design/guest/inquiry/lead-form.tsx` 이고, page 가 선택지를 api 에서 받는다 — 업종 · 도입 예정 시기는 공개 공통코드 `GET /public-code-items?groups=INDUSTRY,PLAN_PERIOD`, 관심 서비스는 `getEnum("LeadInterest")`. 못 받았거나 업종 · 관심 서비스가 비었으면 폼 대신 「다시 시도」를 보이고 서버 로그에 남긴다. 문의자 정보 · 도입 문의 내용 · 동의(수집 항목 · 이용 목적 · 보유 기간) 세 영역이고, 관심 서비스는 체크 상자로 하나 이상(늘어나면 줄을 바꾼다), 업종이 기타(`ETC`)면 업종 아래에 「업종 직접 입력」(50자)이 열린다(LEAD-1). 문의 내용은 필수(2000자), 도입 예정 시기는 선택이다. [문의 접수하기]는 브라우저 검사와, 그것이 놓치는 빈칸만 적은 칸(이름 · 직접 입력 · 문의 내용) · api 와 같은 전화번호 형식 검사(`leadInputProblem`, 그 칸에 검사 오류를 건다) 뒤 확인 창(접수 대상 · 연락할 전화번호 · 이메일 · 영업일 1~2일)을 띄우고, [접수하기](빠르게 두 번 눌러도 한 번만)를 누르면 서버 액션 `submitLead` 가 api `POST /leads` 로 보낸다(사용자 IP 를 `apiHeaders()` 로 넘긴다 — api 가 IP 당 시간 5건을 센다, 10초에 끊는다). 성공하면 완료 창(담당자 연락 일정)을 띄우고 폼을 새로 그린다(key). 완료 창을 닫으면 커서를 접수 버튼으로 돌린다. 서버 액션을 form action 이 아니라 직접 불러, 실패해도 적은 내용이 그대로 남고 버튼 위에 오류와 다시 하는 방법을 보인다. 429(10분 안 같은 전화번호 · 이메일 「이미 접수된 문의가 있습니다…」, IP 한도)와 문장이 모두 한글인 400 은 api 문구를 보인다. api 의 이메일 · 길이 · 관심 서비스 검사는 영문 기본 문구라 400 문장 중 하나라도 영문이면(한글과 섞여도) 입력 확인 문구(`LEAD_INVALID`)로 바꾸고, 시간 초과 · 서버 액션 응답 없음은 이미 접수됐을 수 있다고(`LEAD_UNKNOWN`), 그 밖은 접수 실패(`LEAD_FAILED`)로 보이며 모두 로그에 남긴다(`leadFailureOf`). 폼 값 → api 본문(`leadBodyOf` — 앞뒤 공백 정리, 문의 내용의 줄바꿈은 1자(LF)로 — 폼을 보내면 브라우저가 CRLF(2자)로 바꿔, 화면에서 2000자인 글이 줄이 많으면 api 길이 제한을 넘던 것을 막는다, 업종 직접 입력은 기타일 때만, 고르지 않은 시기는 null), 입력 검사, 실패 문구는 `pnpm test`.

# API

whale-erp-api 를 호출한다. 주소는 `API_BASE_URL` 로 주입한다
(`.env.development` 는 `http://localhost:8000`, `.env.production` 은 비어 있고
배포 환경이 주입한다). 두 파일 모두 git 이 추적하지 않는다.

회원가입은 `POST /auth/signup`(가입, 중복이면 409), `POST /auth/signup/login-id-availability`·`POST /auth/signup/email-availability`(중복 확인, `{ available }`) 셋을 부른다 — api PR #37(bulbasaur 브랜치)에서 들어온다. 사업자정보 진위확인 `POST /auth/signup/business-verifications`(`{ verificationToken }`, 10분)와 가입의 `bizVerificationToken` 은 api lapras 브랜치(#37 위)에서 들어온다.
지금 부르는 엔드포인트는 `POST /auth/admin/login`·`/auth/admin/refresh`·`/auth/admin/logout`·`/auth/admin/password-change`(서버에서만), 그리고 BFF `src/app/api/[...path]/route.ts`(GET 만, 쿠키의 토큰을 붙여 대신 부르고 api 401 이면 세션 쿠키를 지운다)를 거쳐 화면이 부르는 `GET /auth/admin/login-info`(로그인마다 첫 탭에서 한 번)·`/bp-codes/{bpCodeId}/stores`·`/bp-codes/{bpCodeId}/code-items`(플랫폼 계정이 고른 다른 BP 의 탭)다. GNB 「내정보 관리」(MY PAGE, F-AMTDCK > S-JXKHCM)는 `src/lib/my-profile.ts`에서 `GET`·`PATCH /auth/admin/me`·`GET /auth/admin/me/email-availability`를 부른다 — 항상 `CurrentUser()`의 로그인 계정 자신만 보고 고치며, BP 선택(`/bp-switch`)으로 보고 있는 BP 는 건드리지 않는다. 저장은 조회 응답의 `updatedAt`을 함께 보낸다 — platform-admins 수정과 같은 동시 수정 검사(ip-code-review-claude 적대적 리뷰로 찾음, 2026-10-21)라, 저장 뒤 204 응답엔 새 `updatedAt`이 없어 다시 조회해 받는다(`my-page-panel.tsx`). 이메일을 바꿀 때 「지금 비밀번호」를 함께 받아 확인하던 통제(ip-code-review-claude 적대적 리뷰로 찾음, 2026-10-21 — 탈취한 접근 토큰만으로 로그인 이메일을 공격자 주소로 바꿔 비밀번호 찾기를 가로채는 계정 탈취를 막는 것이었다)는 2026-10-22 사용자 결정으로 뺐다 — 이메일 중복 확인만 남았다. api 경로는 있지만 아직 `openapi.json`에 실리지 않아 타입은 손으로 적었다(`src/lib/my-profile-form.ts`가 검사·변환). GNB 같은 묶음의 「비밀번호 변경」(S-PTWREE, `password-change-panel.tsx`)도 같은 모양의 슬라이드 패널로 열었다(2026-10-26) — `session-gate.tsx`가 `myPageOpen`과 같은 자리에 `passwordChangeOpen`을 두고 같은 `myPageTrigger`(UserPop 이름 버튼)로 포커스를 돌린다. 현재 비밀번호·새 비밀번호·새 비밀번호 확인을 받아 `POST /auth/admin/me/password-change`(`src/lib/my-password.ts`, api everest PR 짝 — openapi.json 에는 실렸지만 front 생성 타입은 kabuto 기준이라 아직 안 받아 이 경로도 손으로 적었다)를 부른다 — 세 칸 모두 보기/숨기기 눈 아이콘(`PasswordInput`, 회원가입 `password-field.tsx`와 같은 아이콘 쌍)이 있고, 조건 안내는 칸 안 placeholder로만 두며 칸 아래는 오류가 있을 때만 보인다(2026-10-26 디자인 정리 — 전엔 `passwordChecks` 충족 여부를 칸 아래 늘 보이는 체크리스트로 띄웠는데, 긴 문구가 칸 너비에 잘려 뺐다). 오류 문구는 화면이 만들지 않고 api의 message를 그대로 쓴다 — `myPasswordErrorField`(`my-password-form.ts`)가 "현재 비밀번호가 올바르지 않습니다."만 그 칸, "일치하지 않습니다"는 확인 칸, 나머지 정책 위반은 새 비밀번호 칸으로 가른다. 성공하면 패널을 닫지 않고 완료 화면(연한 파랑 원 + 체크 아이콘, "다음 로그인부터 변경된 비밀번호로 로그인해 주세요")으로 바꾼다. 바꿔도 세션은 끊지 않는다(api와 같은 결정). api 의 견본(items·stock_movements·staff·customers)과 견본 로그인
3팀 화면(main)이 서버 컴포넌트·서버 액션에서 부르는 엔드포인트는 `GET /enums/{name}`(공개)과 `GET` · `POST` · `PUT` · `DELETE /contracts` · `GET /stores/options`(관리자 토큰)다. 점포 화면이 부르는 `/stores` 경로는 위 Layout 의 `src/app/stores/` 항목과 [점포 관리](/stores.md) 구현 절에 적는다. 근로계약의 요청 · 응답 타입은 `src/lib/api-types.generated.ts`(`pnpm openapi:types`)에서 가져온다(`contract-list.ts` 의 `ContractListItem` · `ContractListPage`, `contract-form-model.ts` 의 `CreateContractBody` · `ContractDetail`). `ApiError` 는 응답 본문(`body`)도 들고 있어 409 의 `code` · 목록을 화면이 쓴다. api 의 견본(items·stock_movements·staff·customers)과 견본 로그인
(`POST /auth/customer/login`, `GET /items`)은 2026-10-07 api 와 함께 지웠다(재영 결정).
JWT 액세스 토큰은 `httpOnly` 세션 쿠키(`session`)에 담아 서버에서만 읽고, 매 호출에
`Authorization: Bearer` 로 싣는다. 쿠키는 로그인 서버 액션과 `proxy.ts` 의 갱신이 굽는다.
아직 없는 것: 세션 만료 경고창. 로그인 이력에는 브라우저가 아니라 Next 서버의 IP 가 남는다.
