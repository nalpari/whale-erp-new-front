ERP·플랫폼 레이아웃을 따로 두지 않는다(2026-10-14) — 틀(`src/components/site/admin-frame.tsx`)이 같고, 다른 것은 탭의 서비스로 가른다. 틀 안의 `SessionGate`(`session-gate.tsx`)가 로그인 정보와 이 탭의 서비스·BP·점포·공통코드를 준비할 때까지 로딩 화면을 보이고, 준비되면 `AdminHeader`(`admin-header.tsx`)와 본문을 그린다. 탭의 서비스(`WHALE_ERP`·`PLATFORM`)는 sessionStorage `current-bp` 에 BP 와 함께 둔다 — BP·가맹 계정은 늘 ERP, 플랫폼 계정은 자기 BP 탭이 플랫폼이고 BP 선택기로 연 탭(`?bp=`)이 ERP 다. 탭 값이 없는 새 탭은 주소가 속한 메뉴의 서비스로 정한다(`resolveTab`, `serviceOfPath`). 헤더 메뉴는 그 서비스의 메뉴(`serviceCode`)만 2단계까지(조회 권한이 없는 메뉴는 권한 있는 첫 하위 메뉴로 연결하고, 갈 곳이 없으면 빼며, 사용자 이름 옆 권한 이름은 공통코드 `ROLE_TYPE`), 오른쪽 선택기는 ERP 면 점포 범위·플랫폼이면 BP 선택기(BP 목록 API 대기)다. 그 서비스의 홈이 아니고 그 서비스 메뉴에 없는 주소면 안내 후 `history.back()`(기록이 없으면 홈)이다 — BP 계정이 플랫폼 주소에 오거나 플랫폼 탭에서 ERP 주소를 치면 여기서 막힌다. 훅 `useAccount`·`useService`·`useMenus`·`useMenuRole`·`useStores`·`useCodes`·`useCurrentBp`·`useScope` 로 화면이 읽는다. 로그인 없이 열리는 곳은 공개 경로 목록뿐이고(`src/lib/auth-routes.ts` 의 `isPublicPath` — 모르는 경로는 막는 쪽), 로그인하면 권한 유형 PM·PA 는 `/platform`, 그 밖은 `/home` 으로 간다(`homeOf`). GlobalHeader 로고는 아직 `/` 로 걸려 있다.

* `src/app/(public)/(site)/signup/` - 로그인 전 실제 화면(1팀) 중 BP 회원가입 `/signup`(기본정보·사업자정보 인증(선택)·약관동의·제출)과 가입 완료 `/signup/done`. 로그인(`/login`)과 같은 로그인 전 틀(`(site)/layout.tsx` — `GuestHeader` · `GuestFooter`)을 쓰고, 모양은 ERP 디자인 시스템이 아니라 `docs/demo/src/pages/auth/signup.mjs`·`signup-done.mjs`(`design/guest/sign-up`(아래 항목)을 1팀이 옮긴 것)가 기준이다(2026-10-14~15. 폼 토큰은 `design/guest/guest-form.ts`·`theme.ts`를, 가입 완료는 `design/guest/guest-ui.tsx`의 `GuestPage`·`GuestVisual`·`GuestButton`을 그대로 가져다 쓴다). `auth-routes.ts` 의 공개 경로 `/signup` 아래라 로그인 없이 열린다. 처음엔 `/auth/signup` · `/auth/signup-done` 에 자체 GNB·푸터(`site-page.tsx`)와 로그인 대기 안내창(`login-pending.tsx`)을 두었으나, main 에 로그인과 공개 경로 목록이 들어와 이 자리로 옮기고 그 둘은 지웠다(2026-10-14). `src/app/design/guest/sign-up`(위 항목)과는 별개다: 저곳은 기획 시안을 옮긴 디자인 샘플(요청 안 보냄)이고, 이곳은 실제 API 를 부르는 운영 라우트다. 아이디·이메일은 칸을 벗어날 때 api 로 중복을 확인하고, 제출 전에 확인을 못 마친 칸을 다시 확인해 가입 요청이 중복으로 거절되지 않게 한다. 사업자정보 "인증하기"는 빈 칸과 사업자등록번호 형식(숫자 10자리, 숫자만 입력)을 먼저 보고, 통과하면 서버 액션 `verifyBusiness` 가 api `POST /auth/signup/business-verifications` 를 부른다 — api 가 번호 중복 → 국세청 진위확인을 하고 10분짜리 토큰을 준다. 확인하는 동안은 세 칸·버튼과 가입 버튼이 잠긴다. 토큰과 받은 시각은 화면 상태에만 두고, 가입할 때 `bizVerificationToken` 으로 싣는다. 세 칸이 비어 있으면 사업자정보 없이 가입하지만, 값이 있는데 인증이 없으면(재인증 · 10분 경과 · 가입 거절로 풀린 뒤 포함) 가입 요청을 보내지 않고 「인증하거나 지우기로 비운 뒤」 가입하게 한다(`bizSubmitBlock`) — 보이던 사업자정보가 조용히 빠진 채 가입되지 않게(PR #30 ⑤ 블로커). 받은 지 10분이 지났으면 가입 요청을 보내지 않고 인증을 풀어 다시 인증하게 하고, api 가 가입을 토큰 만료(400)나 사업자번호 중복(409)으로 거절해도 그 문구로 가려(`isBizSignupRejection`) 인증을 풀고 사업자정보 칸에 보인다. 진위확인 실패는 400 · 409 · 422(불일치) · 503(국세청 장애, 로그) 은 api 문구를, 429 · 그 밖은 정해진 문구를 보인다(`_components/biz-verification.ts`). 불일치는 어느 칸이 틀렸는지 몰라 칸 테두리를 빨갛게 하지 않는다. 기본정보 칸은 아이디|이름, 비밀번호|확인, 이메일|연락처, 상호명 순이다(2026-10-13). 가입 완료 화면의 상호명·아이디·이메일은 가입 성공 뒤 서버 액션이 심는 httpOnly 쿠키(`signup-done-cookie.ts`, 10분, 경로는 `SIGNUP_DONE_PATH` 상수 `/signup/done`)로 받는다 — 쿠키가 없거나 깨졌으면 로그인으로 보낸다(명세 `S-UUBGOD`). 서버 액션은 사용자 IP 를 `X-Forwarded-For` 로 api 에 넘긴다 — api 의 IP 한도(가입은 도입문의와 같이 IP 당 1시간 5건)가 방문자별로 세어지려면 api `TRUST_PROXY` 에 이 서버가 있어야 하고, Next 앞에 `X-Forwarded-For` 를 덧붙이거나 덮어쓰는 프록시가 있어야 한다 — Next 는 이 머리말이 이미 있으면 그대로 두므로, 바로 노출되면 브라우저가 지어 보낸 IP 가 api 까지 간다. api 실패는(사업자정보 거절 400 · 409 는 위처럼 따로) 400 · 409 만 api 문구를 그대로 보이고 그 밖(429 · 404 · 5XX)은 정해진 문구로 보이며 서버 로그에 남긴다(`_components/api-failure.ts`). 409 를 받으면 아이디 · 이메일을 다시 확인해 걸린 칸에 오류를 띄우고, 응답을 받았는지 알 수 없는 실패(10초 시간 초과 · 서버 액션 전송 실패)와 api 가 받은 뒤의 실패(응답 모양 · 완료 쿠키)는 「이미 가입되었을 수 있으니 로그인을 먼저 시도해 주세요」로 안내한다. 「웨일ERP 시작하기」와 로그인 링크는 `/login` 으로 간다 — 명세([Auth](/auth.md))는 그 버튼이 로그인 세션을 만들고 홈으로 간다고 하지만, api 에 가입 토큰을 세션으로 바꾸는 경로가 아직 없어 로그인 화면으로 보낸다. 관리자 웹 로그인은 아이디의 대소문자를 구분하고 api 는 가입 아이디를 소문자로 저장하므로, 아이디 칸은 입력하는 순간 소문자로 바꿔 보인다(`normalizeLoginId`) — 대문자로 친 그대로 두면 가입한 아이디를 그대로 쳐서는 로그인할 수 없다(PR #23 ⑤ 블로커). `(site)` 틀 전체가 `design/guest` 의 `GuestHeader`·`GuestFooter` 를 쓰고, 홈·`/login` 본문도 guest 디자인으로 바꿔 더는 두 디자인 시스템이 섞이지 않는다(2026-10-19 — 그 전의 `SiteNav`·`SiteFooter` 는 지웠다). 1720px 최소폭도 틀이 건다. 약관동의의 「내용보기」 팝업(`_components/terms-dialog.tsx`)은 처음 열 때 api 시행 중 약관(`TERMS_SERVICE` · `PRIVACY_COLLECT`)을 받아 `TermsMarkdown` 으로 그린다 — 화면에 보인 버전과 동의 기록 버전이 같다. 목업 문구를 옮겨 두던 `_components/terms.ts` 와 미정 값(`[ ]`) 빨간 표시는 지웠다(2026-10-19).

# API

whale-erp-api 를 호출한다. 주소는 `API_BASE_URL` 로 주입한다
(`.env.development` 는 `http://localhost:8000`, `.env.production` 은 비어 있고
배포 환경이 주입한다). 두 파일 모두 git 이 추적하지 않는다.

회원가입은 `POST /auth/signup`(가입, 중복이면 409), `POST /auth/signup/login-id-availability`·`POST /auth/signup/email-availability`(중복 확인, `{ available }`) 셋을 부른다 — api PR #37(bulbasaur 브랜치)에서 들어온다. 사업자정보 진위확인 `POST /auth/signup/business-verifications`(`{ verificationToken }`, 10분)와 가입의 `bizVerificationToken` 은 api lapras 브랜치(#37 위)에서 들어온다.
지금 부르는 엔드포인트는 `POST /auth/admin/login`·`/auth/admin/refresh`·`/auth/admin/logout`·`/auth/admin/password-change`(서버에서만), 그리고 BFF `src/app/api/[...path]/route.ts`(GET 만, 쿠키의 토큰을 붙여 대신 부르고 api 401 이면 세션 쿠키를 지운다)를 거쳐 화면이 부르는 `GET /auth/admin/login-info`(로그인마다 첫 탭에서 한 번)·`/bp-codes/{bpCodeId}/stores`·`/bp-codes/{bpCodeId}/code-items`(플랫폼 계정이 고른 다른 BP 의 탭)다. api 의 견본(items·stock_movements·staff·customers)과 견본 로그인
3팀 화면(main)이 서버 컴포넌트·서버 액션에서 부르는 엔드포인트는 `GET /enums/{name}`(공개)과 `GET` · `POST` · `PUT` · `DELETE /contracts` · `GET /stores/options`(관리자 토큰)다. 점포 화면이 부르는 `/stores` 경로는 위 Layout 의 `src/app/stores/` 항목과 [점포 관리](/stores.md) 구현 절에 적는다. 근로계약의 요청 · 응답 타입은 `src/lib/api-types.generated.ts`(`pnpm openapi:types`)에서 가져온다(`contract-list.ts` 의 `ContractListItem` · `ContractListPage`, `contract-form-model.ts` 의 `CreateContractBody` · `ContractDetail`). `ApiError` 는 응답 본문(`body`)도 들고 있어 409 의 `code` · 목록을 화면이 쓴다. api 의 견본(items·stock_movements·staff·customers)과 견본 로그인
(`POST /auth/customer/login`, `GET /items`)은 2026-10-07 api 와 함께 지웠다(재영 결정).
JWT 액세스 토큰은 `httpOnly` 세션 쿠키(`session`)에 담아 서버에서만 읽고, 매 호출에
`Authorization: Bearer` 로 싣는다. 쿠키는 로그인 서버 액션과 `proxy.ts` 의 갱신이 굽는다.
아직 없는 것: 세션 만료 경고창. 로그인 이력에는 브라우저가 아니라 Next 서버의 IP 가 남는다.
