# Manyfast 명세를 Plane 작업으로 옮기는 규칙

Manyfast에 쓴 명세를 Plane 프로젝트의 모듈과 작업으로 옮기는 방법을 적는다.
**어느 팀, 어느 Manyfast 프로젝트든 같은 방식으로 쓸 수 있게** 규칙을 먼저 적고,
WHALE ERP 3팀이 실제로 만든 결과를 뒤에 예로 붙인다.

기준일 2026-09-22 · 정한 사람 재영 · 옮긴 세션 기획

---

## 1. 무엇을 Plane에 넣는가

Plane은 **할 일을 두는 곳**이다. 요구사항과 명세의 원본은 Manyfast, 화면은 목업, 운영 규칙은
정책 문서에 있다. Plane에는 그것들을 가리키는 작업만 둔다. 같은 내용을 두 곳에 적지 않는다.

계층은 두 층이다.

| 층 | 무엇 | 어디서 왔나 |
|---|---|---|
| 맨 위 | **명세 작업** | Manyfast 명세 하나에 작업 하나. 이름은 명세 이름 그대로 |
| 그 아래 | **개발 작업** | 명세 하나를 층과 화면으로 쪼갠 것 |

**기능 부모는 두지 않는다.** Manyfast의 기능(F-)을 작업으로 만들어 명세를 그 밑에 달면 층이
하나 늘 뿐 쓸모가 없다. 명세가 최상위다.

**결정 대기는 Plane에 두지 않는다.** 아직 정하지 못한 것은 목업의 쟁점 블록에 두고, 외부
검토가 필요한 것만 「[점검]」 작업 하나로 모은다. Plane에 결정 항목을 늘어놓으면 작업 목록과
섞여 무엇을 할 차례인지 흐려진다.

**사이클은 쓰지 않는다.** 착수 순서는 명세 본문과 선행 관계(`blocked_by`)로 나타낸다.

## 2. 프로젝트마다 먼저 정할 것

다른 Manyfast 프로젝트에 이 규칙을 쓰려면 아래 다섯을 자기 것으로 바꾼다.

| 항목 | 무엇 | WHALE ERP 3팀의 값 |
|---|---|---|
| 워크스페이스·프로젝트 | Plane 주소 | `whale-erp` / WhaleERP |
| `external_source` | 중복 방지 표시. 팀마다 다른 값을 쓴다 | `whale-plan` |
| **층** | 작업을 어느 갈래로 나눌지. 제품의 화면 구성에 맞춘다 | `[API]` `[관리자웹]` `[직원앱]` `[점검]` |
| **영역 라벨** | 모듈마다 붙는 업무 갈래 | 기반·직원·근무·지원·출퇴근·알림·직원 알림·선행 조건 |
| **모듈** | 기능 단위 묶음 (3장) | 15개 |

층은 제품마다 다르다. 웹 하나뿐인 제품이라면 `[API]` `[웹]` `[점검]` 셋으로 충분하고, 앱이
여럿이면 앱마다 하나씩 둔다. **화면이 없는 것은 `[API]`, 화면에도 서버에도 매이지 않는 확인
거리는 `[점검]`**으로 두는 두 가지는 어디서나 같게 쓴다.

## 3. 모듈은 기능 단위로 나눈다

Manyfast 요구사항(R-)의 묶음을 그대로 모듈로 쓰지 않는다. 요구사항은 덩어리가 커서 어디에
무엇이 있는지 알기 어렵다. **한 화면 묶음이나 한 업무 흐름**을 모듈 하나로 한다.

나누는 눈금 셋.

1. 모듈 하나에 명세 1~4건이 들어가면 알맞다. 5건을 넘으면 쪼갠다
2. 사용자가 그 일을 하나로 여기면 한 모듈이다 — "채용해서 계약 맺기"는 명세가 넷이어도 한 모듈
3. 화면에 매이지 않는 것(배치·발송 기반·외부 검토·다른 팀 선행)은 **「공통 기반」** 한 모듈에 모은다

모듈 설명에 `담는 명세: …`를 적어 둔다.

**모듈을 넘는 선행도 건다.** 두 모듈이 같은 데이터 구조를 쓰면 작업을 한 번만 만들고 다른
모듈의 작업이 그것을 선행으로 건다. 같은 것을 두 번 만들면 나중에 한쪽만 고쳐진다.

## 4. 작업 규칙

### 제목

`[층] 하는 일` 꼴로 쓴다. 명세 작업과 묶음 작업에는 층을 붙이지 않는다.

```
[API] 근로계약 데이터 구조
[관리자웹] 근로계약서 초안 작성 화면
[직원앱] 필기 서명 날인과 거부
[점검] 출퇴근 등록 권한과 좌표 비저장 점검
```

이름 안에 층을 또 넣지 않는다. "관리자 웹 · 근로계약서 초안 작성 화면"처럼 쓰지 않고,
`[API]` 작업 이름 끝의 "API"도 겹치니 뺀다 — "TO-DO 목록 조회 API"가 아니라
"[API] TO-DO 목록 조회"다.

### 본문

「완료 조건」을 목록으로 적고 맨 아래에 「명세」 이름을 적는다.

```html
<p><b>완료 조건</b></p>
<ul><li>…</li><li>…</li></ul>
<p><b>명세</b> TO-DO 관리</p>
```

완료 조건은 **명세 슬롯의 문장을 그 작업 몫만 골라 옮긴 것**이다. 새로 지어내지 않는다.
확정된 쟁점은 문장 끝에 쟁점 번호를 괄호로 붙인다.

```
하단 탭을 따로 두지 않는다(WORK-2).
퇴직한 뒤에도 급여 탭에서 보존 기간 동안 조회한다(PAY-4).
```

**명세에 아직 없는 결정을 적을 때는 그 사실을 완료 조건에 남긴다.** 예: "명세에 이 문장을
더해야 한다." 그리고 그 자리에서 Manyfast 수정 제안을 보낸다. 제안이 승인되면 이 표시를 지운다.

### 그 밖

- **부모** — 개발 작업은 그 명세 작업을 부모로 둔다
- **선행** — 착수 순서는 `blocked_by` 관계로 건다. 데이터 구조 → API → 화면이 기본 흐름이다
- **중복 방지** — 모든 작업에 `external_source`와 `external_id`(작업 키)를 넣는다. 다시 돌려도
  같은 `external_id`면 새로 만들지 않는다
- **상태** — Backlog · Todo · In Progress · Done · Cancelled 다섯을 그대로 쓴다.
  다음 단계로 미룬 것은 Done이 아니라 **Cancelled**로 두고 이유를 댓글로 남긴다
- **담당자** — 사람이 정해지기 전에는 비워 둔다

### 조회·수정·삭제를 빠뜨리지 않기

**Manyfast 명세는 조회를 `display` 슬롯에만 적는 일이 많다.** "화면은 이러이러하게 보인다"로만
적혀 있어서 화면 작업만 만들고 그 화면이 읽을 조회 API 를 빼먹기 쉽다. 실제로 우리도 근로계약·
급여명세서·커뮤니티에서 조회 API 작업을 빠뜨렸다가 뒤늦게 메웠다 (2026-09-21).

모듈 하나를 다 쓰고 나면 이 넷을 확인한다.

1. **화면 작업마다 그 화면이 읽을 조회 API 작업이 있는가** — 목록 화면이면 목록 조회, 상세
   화면이면 상세 조회
2. **만든 것을 고치는 길이 있는가** — 저장 작업은 있는데 수정 작업이 없는 곳
3. **지우는 길이 있는가** — 지우지 않는 것이 정책이면 그 사실을 완료 조건에 적는다
4. **읽기 전용 명세는 1~3이 없는 것이 맞다** — 이메일 찾기, 알림함 확인, 대시보드 조회 같은 것

`rules` 나 `exceptions` 에 "…할 수 있다"가 있는데 그에 맞는 작업이 없으면 빠진 것이다.
명세 자체에 없으면 Manyfast 수정 제안으로 먼저 채운다.

## 5. 만드는 순서

1. **Manyfast 명세를 읽는다.** 프로젝트를 통째로 읽어 명세의 슬롯(preconditions·trigger·action·
   outcome·exceptions·display·permissions·rules·dataSpec)을 본다
2. **모듈을 정한다.** 3장의 눈금으로 나누고 Plane에 모듈을 만든다
3. **모듈 하나씩 정의 파일을 쓴다.** 6장의 형식대로
4. **러너를 돌린다.** 명세 작업 → 개발 작업 → 모듈 담기 → 선행 걸기가 한 번에 된다
5. **조회·수정·삭제를 빠뜨렸는지 본다.** 4장의 점검 넷. 빠진 것은 정의 파일에 더해 러너를 다시
   돌린다. 이미 있는 것은 건너뛰므로 새 작업만 생긴다
6. **명세에 빠진 것을 찾으면 그 자리에서 Manyfast 수정 제안을 보낸다.** 작업을 만들다 보면
   결정했는데 명세에 없는 것이 드러난다. 모아 두지 말고 바로 보낸다

## 6. 정의 파일 형식

모듈 하나에 파일 하나다. 파이썬 파일이지만 실제로는 자료만 담는다.

```python
MODULE = "채용·근로계약"      # Plane 모듈 이름과 똑같이
TRACK  = "직원"               # 이 모듈의 모든 작업에 함께 붙는 영역 라벨

SPECS = [
 dict(key="spec-근로계약서 초안 작성과 발송",   # external_id. 겹치지 않게
      name="근로계약서 초안 작성과 발송",        # Plane에 보일 이름 = 명세 이름
      mf="S-OIILIW",                            # Manyfast 명세 ID. 없으면 빼도 된다
      layers=["웹"],                            # 이 명세가 걸치는 층 → 라벨이 된다
      html="<p>명세를 두세 문장으로 줄인 것</p>"),
]

T = [
 dict(key="con-api-model",        # external_id. 선행을 걸 때 이 키로 가리킨다
      spec="근로계약서 초안 작성과 발송",   # 부모가 될 명세의 name
      name="근로계약 데이터 구조",          # 층 접두는 러너가 붙인다
      layer="API",                          # 웹 · 앱 · API · 확인
      pr="urgent",                          # urgent · high · medium · low
      after=["…"],                          # 선행 작업의 key. 다른 모듈 키도 된다
      done=["완료 조건 한 줄", "또 한 줄"]),
]
```

`after`에는 **다른 모듈의 키도 쓸 수 있다.** 그 모듈을 먼저 만들어 두면 된다.
러너가 키와 Plane 작업 id의 짝을 `ids.json`에 쌓아 두고 찾아 쓴다.

층 이름(`웹`·`앱`·`API`·`확인`)과 제목 접두의 짝은 러너 맨 위에 있다. 다른 프로젝트는 여기를
자기 층으로 바꾼다.

```python
LAYER  = {"웹": "관리자 웹", "앱": "직원 근무 앱", "API": "API", "확인": None}
PREFIX = {"웹": "[관리자웹]", "앱": "[직원앱]", "API": "[API]", "확인": "[점검]"}
```

## 7. 스크립트

`docs/plane/scripts/` 에 있다. 파이썬 3만 있으면 돌고 설치할 것이 없다.

| 파일 | 하는 일 |
|---|---|
| `plane_api.py` | Plane REST v1 을 부르는 공통 함수(`call`·`get_all`·`esc`). 프로젝트 값은 환경변수로 받는다 |
| `run_module.py` | **러너.** 정의 파일 하나를 읽어 명세와 개발 작업을 만들고 모듈에 담고 선행을 건다 |
| `example_tasks.py` | 정의 파일 본보기. 필드마다 뜻을 주석으로 달아 두었다 |
| `ids.json` | 작업 키와 Plane 작업 id 의 짝. 러너가 만들고 쌓는다 (저장소에 두지 않는다) |

### 쓰는 법

토큰을 먼저 만든다. Plane 웹의 프로필 → 설정 → Developer → 퍼스널 액세스 토큰이고,
주소에 워크스페이스 슬러그가 들어가지 않는다 — `/settings/profile/api-tokens/`.
만든 값을 파일에 넣고 그 파일만 읽게 한다. **토큰을 명령줄이나 채팅에 적지 않는다.**

```bash
mkdir -p ~/.config/plane-mcp && chmod 700 ~/.config/plane-mcp
# 편집기로 ~/.config/plane-mcp/api-key 에 토큰을 넣는다
chmod 600 ~/.config/plane-mcp/api-key
```

프로젝트 값을 환경변수로 준다. 자기 프로젝트 것으로 바꾼다.

```bash
export PLANE_BASE=http://172.30.1.65:3333
export PLANE_SLUG=whale-erp
export PLANE_PROJECT=<프로젝트 UUID>
export PLANE_SOURCE=<우리 팀 표시>        # 예: whale-plan

python3 plane_api.py                      # 설정이 맞는지 본다
python3 run_module.py example_tasks       # 모듈 하나를 만든다
```

러너를 돌리기 전에 **모듈과 라벨은 Plane 에 먼저 만들어 둔다.** 없으면 러너가 이름을 대며
멈춘다. 이미 있는 `external_id` 는 건너뛰므로 정의 파일을 고쳐 다시 돌려도 새로 생기지 않는다.
이미 만든 작업의 본문을 고치려면 그 작업만 따로 `PATCH` 한다.

주의할 것 넷.

1. **호출 간격 1.1초.** 분당 제한이 있어 더 빠르게 돌리면 429 가 난다. `plane_api.INTERVAL` 에 있다
2. **부모를 지우기 전에 자식이 풀렸는지 확인한다.** 그러지 않으면 자식까지 함께 지워진다
3. **커뮤니티 판에는 작업 유형과 Epic API 가 없다.** 계층은 부모-자식으로만 만든다
4. **웹훅이 돌면 알림이 나간다.** 한꺼번에 많이 바꿀 때는 중계기를 잠시 멈춘다 (9장)

## 8. WHALE ERP 3팀의 실제 구성

규칙을 이렇게 적용했다. 다른 프로젝트는 이 표를 자기 것으로 갈아 끼운다.

명세 작업 27건 + 「공통 기반」 묶음 1건 + 개발 작업 198건 = **226건**.

| 모듈 | 작업 | 담는 명세 |
|---|---|---|
| 비로그인 홈 | 13 | 서비스 및 계정 진입 · 공지사항·FAQ 열람 · 도입문의 등록 |
| 로그인 후 홈·업무 범위 | 12 | 업무 범위 고정 및 바로가기 · 홈 현황 요약과 처리 대기 |
| 채용·근로계약 | 39 | 근로계약서 초안 작성과 발송 · 직원 초대와 가입 확인 · 초대 확인과 계약서 날인 · 날인 확인과 계약 상태 관리 |

층별로는 `[API]` 94, `[관리자웹]` 46, `[직원앱]` 40, `[점검]` 18건이다.

정의 파일 열다섯(`contract`·`login`·`staffinfo`·`schedule`·`todo`·`attendance`·`payroll`·
`opsnotify`·`staffnotify`·`support`·`community`·`public`·`adminhome`·`apphome`·`base`)은
우리 제품 내용이라 저장소에 두지 않고 기획 세션의 작업 폴더에 있다. 필요하면 기획 세션에 청한다.
`docs/plane/scripts/example_tasks.py` 가 그 가운데 TO-DO 모듈을 본보기로 옮겨 놓은 것이다.

라벨은 관리자 웹 · 직원 근무 앱 · API에 영역 라벨 여덟(기반·직원·근무·지원·출퇴근·알림·
직원 알림·선행 조건)을 쓴다. 「결정 대기」와 「외부 검토」 라벨은 초기화 전 구조에서 쓰던
것이라 지금은 붙이지 않지만, 왜 없는지 모르게 되므로 지우지 않고 둔다.

## 9. 우리 환경에 붙어 있는 것

여기부터는 WHALE ERP 3팀 환경이다. 다른 팀은 자기 환경으로 바꿔 읽는다.

- **Plane**: 미니(`http://172.30.1.65:3333`)의 셀프호스팅 커뮤니티 판
- **BUZZ 알림**: Plane 웹훅 → 미니 `~/buzz-bridge/bridge.py` → BUZZ 「Whale ERP 알림봇」 채널.
  작업이 생기거나 상태·담당자·목표일·우선순위가 바뀌거나 댓글이 달리면 보낸다.
  한꺼번에 많이 바꿀 때는 미리 멈춘다.

  ```
  ssh ljy-mini@172.30.1.65 'launchctl unload ~/Library/LaunchAgents/com.whale.buzz-bridge.plist'
  # 일이 끝나면
  ssh ljy-mini@172.30.1.65 'launchctl load ~/Library/LaunchAgents/com.whale.buzz-bridge.plist'
  curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8787/health   # 200 이어야 한다
  ```

- **Plane MCP**: 각자 자기 컴퓨터에 설정한다. 서버에 한 번 올려 두고 함께 쓰는 것이 아니다.
  토큰이 사람마다 달라야 누가 무엇을 했는지 남는다. 설정 방법은 별도 안내서에 있다
- **담당자별 진행 상황**: `/whale-erp/analytics/work-items/` 의 Customized Insights 에서
  Assignee 와 State group 을 고르면 사람마다 어디까지 했는지 본다
