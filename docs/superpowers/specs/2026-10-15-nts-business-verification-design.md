# 국세청 사업자등록번호 진위확인 — 회원가입 연동 설계

날짜: 2026-10-15 · 작성: 김지영(Claude 협업)

## 목적

BP 회원가입(`/signup`)의 「사업자정보 인증(선택)」은 지금 빈 칸과 번호 형식만 보고 「인증완료」를 띄우는 자리표시자다.
이를 국세청 진위확인에 실제로 잇고, 인증한 사업자정보를 가입할 때 `bp_codes` 에 저장한다.

## 범위

- 포함: api 진위확인 엔드포인트 · 국세청 클라이언트 · 10분 인증 토큰 · 가입 시 저장, front `/signup` 인증하기 연동, okf 정정.
- 제외:
  - 대표자 연락처·이메일·주소·업태·종목 입력. 회원가입에는 이 칸이 없다. BP 마스터 마이페이지와 점포 등록/수정에서 다룬다(2026-10-15 사용자 확인).
  - 마이페이지·점포 화면의 진위확인. 그 화면을 만들 때 이번 클라이언트·토큰을 다시 쓰고 경로는 각자 붙인다.
  - 휴업·폐업 판정. 진위만 확인한다(`okf/auth.md` — `S-RCJXIG` · `S-VRNTHD`).

## 1. api

### 1-1. `POST /auth/signup/business-verifications`

요청은 `{ bizRegistrationNumber, bizCeoName, bizOpenDate }` 다.

- `bizRegistrationNumber`: 숫자 10자리.
- `bizCeoName`: 앞뒤 공백 제거, 1자 이상.
- `bizOpenDate`: `YYYY-MM-DD`. 국세청에는 `YYYYMMDD` 로 보낸다.

순서:

1. **중복 검사를 먼저 한다**(`PL-OCJOFP`). 같은 번호를 쓰는 다음 행이 있으면 409 `이미 등록된 사업자등록번호입니다.` 를 돌려준다. 누가 쓰는지는 알리지 않는다.
   - `bp_codes`: `is_deleted = false` 이고 `account_status_code` 가 탈퇴가 아닌 행. 탈퇴·삭제한 BP 의 번호는 다시 쓸 수 있다.
   - `store_business_profiles`: 삭제되지 않은 점포의 행.
2. 국세청 `POST https://api.odcloud.kr/api/nts-businessman/v1/validate?serviceKey=…` 를 부른다. 본문은 `{ businesses: [{ b_no, start_dt, p_nm }] }` 다.
3. `data[0].valid === "01"` 이면 성공이다. 10분짜리 JWT 를 `{ verificationToken }` 으로 돌려준다.
   - 페이로드: `{ typ: 'biz-verification', bizRegistrationNumber, bizCeoName, bizOpenDate }`
   - 가입 완료 토큰과 같은 `JwtService` 로 서명하고, `typ` 으로 구분한다.

실패 응답:

| 경우 | 상태 | 문구 |
|---|---|---|
| 형식 오류 | 400 | 칸별 검증 문구 |
| 번호 중복 | 409 | 이미 등록된 사업자등록번호입니다. |
| 국세청 불일치(`valid === "02"`) | 422 | 입력한 사업자정보가 국세청 정보와 일치하지 않습니다. |
| 국세청 장애 · 시간 초과 · 키 없음 · 뜻밖의 응답 | 503 | 국세청 확인이 원활하지 않습니다. 잠시 후 다시 시도해 주세요. |

503 은 서버 로그를 남긴다. 키 값과 요청 원문은 로그에 남기지 않는다.

### 1-2. `NtsBusinessClient`

국세청 호출만 맡는다. 입력은 번호·대표자명·개업일자, 결과는 `'MATCH' | 'MISMATCH'` 다. 그 밖의 경우는 예외로 던진다.

- 시간 제한은 5초다.
- 키가 비어 있으면 운영(`isProduction()`)에서는 기동을 멈춘다. 개발에서는 기동하되 호출하면 503 이 된다.
- 테스트에서는 이 클래스를 대신 끼운다. 단위 테스트는 국세청을 부르지 않는다.

### 1-3. `SignupDto.bizVerificationToken` (선택)

- 토큰이 있으면 서명·만료·`typ` 을 확인한다. 실패하면 400 `사업자정보 인증이 만료되었습니다. 다시 인증해 주세요.` 를 돌려준다.
- 가입 트랜잭션 안에서 1-1 의 중복 검사를 한 번 더 한다. 인증한 뒤 다른 BP 가 먼저 가입했으면 409 다.
- 저장하는 값은 토큰에서만 꺼낸다: `bp_codes.biz_registration_number` · `biz_ceo_name` · `biz_open_date` · `biz_verified_at`(가입 시각).
- 토큰이 없으면 지금처럼 `biz_*` 를 비워 둔다.
- `openapi:export` 를 다시 돌려 `openapi/openapi.json` 을 커밋한다.

## 2. front (`/signup`)

화면 모양(세 칸, 인증하기·재인증·지우기, 「인증완료」 배지)은 바꾸지 않는다.

### 2-1. 인증하기

1. 화면에서 먼저 확인한다(빈 칸·번호 10자리). 걸리면 api 를 부르지 않는다.
2. 서버 액션 `verifyBusiness()`(`actions.ts`)가 api 를 부른다. 기다리는 동안 버튼은 「인증 중…」이고, 세 칸과 버튼이 잠긴다. 연타해도 요청은 한 번만 나간다.
3. 성공하면 「인증완료」로 바꾼다. 토큰과 받은 시각은 화면 상태에만 둔다. 떠나거나 새로 고치면 사라진다(`F-JVTPSU`).
4. 실패하면 api 문구를 지금 오류 자리(`role="alert"`)에 보이고, 입력값은 남긴다.
   - 불일치는 어느 칸이 틀렸는지 알 수 없어서 칸 테두리를 빨갛게 하지 않는다.
   - api 문구가 없는 실패(연결 실패 등)에는 `사업자정보를 확인하지 못했습니다. 잠시 후 다시 시도해 주세요.` 를 보인다.

### 2-2. 재인증 · 지우기

동작은 지금과 같다. 둘 다 들고 있던 토큰을 버린다.

### 2-3. 가입하기

- 인증했으면 `bizVerificationToken` 을 싣는다. 인증하지 않았으면 싣지 않는다.
- 인증한 지 10분이 지났으면 가입 요청을 보내지 않는다. 인증 상태를 풀고 사업자정보 칸에 `인증 시간(10분)이 지났습니다. 다시 인증해 주세요.` 를 보인다.
- 그래도 api 가 토큰을 거절하면(시계 차이 등), 다른 가입 실패와 같은 자리에 api 문구를 보인다.

### 2-4. 테스트

api 응답을 화면 상태로 바꾸는 부분을 순수 함수로 빼고 단위 테스트를 붙인다. 경우는 성공 · 409 · 422 · 503 · 문구 없는 실패 · 10분 만료다.

## 3. 문서

- `okf/auth.md` 「가입」 절에서 「인증에 성공해야 대표자 연락처·…선택 입력이 열린다」를 회원가입에서 뺀다. 그 칸들은 마이페이지·점포의 일이다(근거: 2026-10-15 사용자 확인). 토큰·중복 규칙 줄은 실제 구현에 맞춘다.
- `okf/whale-erp-front.md` 의 signup 설명에서 "진위확인 연동 전" 문구를 고친다. `generated.at` 을 갱신하고 `okf/log.md` 에 한 줄 남긴다.
- api 쪽 okf 도 같은 규칙으로 고친다.
- 코드 주석: `biz-auth-section.tsx` · `actions.ts` · api `admin-signup.service.ts` 의 "연동 없음" 주석을 현재 동작으로 바꾼다.

## 정해진 것

- 국세청 호출과 중복 검사는 api 에서 한다. front 는 토큰만 나른다.
- 토큰은 10분이고, 가입할 때 한 번 쓴다.
- 진위만 본다. 휴업·폐업은 막지 않는다.
- 회원가입에는 세 칸만 둔다.
